# v1.5.2 · 修复 MuMu/安卓端无法自动战斗

## 中文

### 问题现象

在 MuMu 等安卓模拟器上运行每日任务，进入战斗后立即崩溃或卡住，任务反复重启，表现为
「MuMu 无法自动战斗」。日志里能搜到：

```
AttributeError: 'NoneType' object has no attribute 'perform'
```

（对应日常任务截图里那个 `DailyTask_AttributeError`。）PC 客户端与云游戏不受影响。

### 根因：安卓端当前角色下标恒为 -1

`AndroidDailyTask` 走 ADB/模拟器设备通道（`is_adb() == True`），所有队伍判定进入
`BaseWWTask.in_team_android()`。安卓客户端的队伍栏是**圆形角色头像**，没有 PC 端的
`1/2/3` 数字徽章，`char_N_text` 模板匹配不上，所以之前的实现无法识别当前出战角色，
直接返回 `current_index = -1`。这一下 -1 在战斗链路里引发了连锁崩溃：

1. `load_chars()` 用 `char.index == current_index` 标记当前角色。角色下标是 `0/1/2`，
   永远不等于 -1，于是**没有任何角色被标记为当前角色**。
2. `get_current_char()` 找不到 `is_current_char=True` 的角色，**返回 `None`**。
3. `combat_once()` 的 `self.get_current_char().perform()` 对 `None` 调用 `perform()`
   → `AttributeError`，战斗刚进入就崩。`refresh_cd()` / `get_cd()` 里的 `.index`
   也会抛同样错误。
4. 即使扛过上面这步，切人流程 `switch_next_char()` 靠
   `current_index == switch_to.index` 判定切人成功，`current_index` 恒为 -1 时
   **永远判定失败**，等 10 秒后抛 `raise_not_in_combat('failed switch chars')`，
   切一次人就把战斗打断。

### 修复

核心思路：安卓端既然无法从画面读出当前角色下标，就由脚本自己维护一个**逻辑下标**，
让战斗链路始终拿得到「当前角色」，PC/云游戏分支完全不动。

**1. `BaseWWTask.in_team_android()`：返回逻辑下标而非 -1**

- 新增实例字段 `_android_current_index`（初始 0）。`in_team_android()` 返回它，
  并对越界/非法值回落到 0。
- 每日任务主流程只消费 `in_team()[0]`（是否在队伍），不受影响；
  `in_team_and_world()` / `is_main()` / `ensure_main()` 行为不变。
- 黑帧、不在大世界时仍返回 `-1`，与原来一致，并保留全黑帧 warning。

**2. `BaseCombatTask.get_current_char()`：安卓端兜底选角**

- 当 `is_current_char` 全为 False 时，安卓端按逻辑下标兜底选一个角色并标记为当前，
  不再返回 `None`；逻辑下标越界时回落到第一个非空角色。
- PC 端行为不变：仍返回 `None`，不引入新语义。

**3. `refresh_cd()` / `get_cd()`：防空**

- 当前角色缺失时 `refresh_cd()` 安全跳过、`get_cd()` 返回 0，不再读 `None.index`。

**4. `combat_once()`：当前角色缺失时重载重试**

- 循环里若 `get_current_char()` 仍为 `None`，重新 `load_chars()` 并短暂休眠后继续，
  而不是让 `.perform()` 抛 `AttributeError` 打断战斗。

**5. `switch_next_char()`：切人后同步安卓逻辑下标**

- 安卓端发出切人键后，主动把 `_android_current_index` 推进到目标角色下标。
  这样下一轮 `in_team()` 返回的新下标就能与 `switch_to.index` 相等，
  切人判定成功，不再等 10 秒抛异常。

### 部署范围

改动的两个文件 `BaseWWTask.py`、`BaseCombatTask.py` 都在 `restore.py` 的 32 文件清单中，
已同步到 `working` 与 `repo` 两处并校验哈希一致。新增测试 `tests/TestAndroidCombatFix.py`
属于测试文件，不进部署清单，不影响运行目录。

### 验证

- 新增 `tests/TestAndroidCombatFix.py`：**13 项断言全绿**，覆盖
  `in_team_android()` 返回逻辑下标并保留推进值/越界回落/黑帧分支、
  `get_current_char()` 按逻辑下标兜底/越界回落/PC 端行为不变/已有当前角色不覆盖、
  `refresh_cd` / `get_cd` 防空、切人同步与 combat_once 防空的源码级断言。
- 回归：`TestCloudCombatFixes` 4 项、`TestRahaiFaults` 5 项 —— 全绿。
- 三处（仓库 / `working` / `repo`）改动文件哈希一致，`py_compile` 通过。

## English

### Symptom

Running daily tasks on MuMu or another Android emulator, the task crashes or stalls as
soon as combat starts and gets restarted repeatedly — "MuMu cannot auto-combat". The log
contains:

```
AttributeError: 'NoneType' object has no attribute 'perform'
```

(the `DailyTask_AttributeError` captured in the daily-task screenshots). The PC client
and cloud game are unaffected.

### Root cause: the Android current-character index was always -1

`AndroidDailyTask` runs through the ADB/emulator device channel (`is_adb() == True`), so
all party checks go through `BaseWWTask.in_team_android()`. The Android client shows
**circular character portraits** instead of the PC's `1/2/3` number badges, so the
`char_N_text` templates never match, and the old implementation could not identify the
active character — it returned `current_index = -1`. That single `-1` cascaded through
the combat pipeline:

1. `load_chars()` marks the active character with `char.index == current_index`.
   Character indices are `0/1/2`, never -1, so **no character was ever marked active**.
2. `get_current_char()` found no `is_current_char=True` character and **returned `None`**.
3. `combat_once()` called `self.get_current_char().perform()` → `AttributeError` on
   `None`, crashing the moment combat started. The `.index` reads in `refresh_cd()` /
   `get_cd()` failed the same way.
4. Even past that, `switch_next_char()` decides a switch succeeded via
   `current_index == switch_to.index`. With `current_index` stuck at -1 it **never
   succeeded**, and after 10 seconds threw
   `raise_not_in_combat('failed switch chars')` — interrupting combat on every switch.

### The fix

Since the Android client exposes no readable active-character index, the script now
maintains a **logical index** of its own so the combat pipeline always has a current
character. The PC/cloud branches are untouched.

**1. `BaseWWTask.in_team_android()` returns a logical index instead of -1**

- New instance field `_android_current_index` (starts at 0). `in_team_android()` returns
  it, falling back to 0 for out-of-range or invalid values.
- The daily-task flow only consumes `in_team()[0]` (in party or not), so it is
  unaffected; `in_team_and_world()` / `is_main()` / `ensure_main()` behave the same.
- Black frames and "not in world" still return `-1` as before, with the black-frame
  warning preserved.

**2. `BaseCombatTask.get_current_char()` falls back to a character on Android**

- When all `is_current_char` flags are False, Android mode picks a character by the
  logical index and marks it active instead of returning `None`; an out-of-range index
  falls back to the first non-None character.
- PC behaviour is unchanged: it still returns `None`, introducing no new semantics.

**3. `refresh_cd()` / `get_cd()` guard against a missing character**

- With no current character, `refresh_cd()` skips safely and `get_cd()` returns 0 — no
  more reads of `None.index`.

**4. `combat_once()` reloads and retries when the character is missing**

- If `get_current_char()` is still `None` inside the loop, it calls `load_chars()`
  again, sleeps briefly and continues, rather than letting `.perform()` raise
  `AttributeError` and break combat.

**5. `switch_next_char()` syncs the Android logical index after switching**

- On Android, after sending the switch key, `_android_current_index` is actively
  advanced to the target character's index. The next `in_team()` call then returns a
  matching index, the switch is recognised as successful, and the 10-second timeout
  exception no longer fires.

### Deployment scope

The two changed files, `BaseWWTask.py` and `BaseCombatTask.py`, are both in `restore.py`'s
32-file list and have been synced to both `working` and `repo` with matching hashes. The
new test `tests/TestAndroidCombatFix.py` is a test file, is not part of the deployment
list, and does not affect the runtime directories.

### Validation

- New `tests/TestAndroidCombatFix.py`: **13 assertions, all green** — covering
  `in_team_android()` returning the logical index (with preserved advance, out-of-range
  fallback and black-frame branch), `get_current_char()` fallback by logical index /
  out-of-range fallback / unchanged PC behaviour / no override of an existing current
  character, the `refresh_cd` / `get_cd` guards, and source-level assertions for the
  switch sync and `combat_once` guard.
- Regression: `TestCloudCombatFixes` 4 and `TestRahaiFaults` 5 — all green.
- The changed files match across the repository, `working` and `repo`; `py_compile`
