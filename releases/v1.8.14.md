# v1.8.14 · MuMu 方块拖拽改用 input motionevent（修复落点错位）/ MuMu Blocks drag via input motionevent

本版改了运行时代码，**必须重跑 `python restore.py` 并重启 ok-ww** 才生效。

## 现象

v1.8.13 及之前，MuMu 下方块拖拽的落点始终对不上预览：

```
Placement preview did not match: slot=0, turns=0, row=3, col=1
无尽模式挑战失败：连续三次未能匹配落点预览。
```

`turns=0` 表示这一步根本不需要旋转，纯拖拽就失败了。用户反馈「方块移动不到预期位置，离预期位置高度差很远」。

## 根因（确认）

拖拽走的是 `sendevent` 直接写 Linux input 设备 `/dev/input/event4`，坐标换算在 `game_to_touch()`：

```python
tx = gy / GAME_H * physical_w   # = gy × 0.9375
ty = gx / GAME_W * physical_h   # = gx × 0.9375
```

游戏是横屏 1920x1080（逻辑 2048x1152），物理触屏是竖屏 1080x1920，**两者宽高互换，必须做 90° 旋转（要翻转一个轴）**。而上面的代码只做了转置 `(gy, gx)`，等于**沿对角线镜像**——两个轴都没翻。于是画面上一个点 (x, y) 被送成了完全不同的物理位置，纵轴偏差尤其大，正好对应「高度差很远」。

逐项排除确认不是其它原因：
- 触控设备 ABS 轴范围实测 `X max=1080 / Y max=1920`，`physical_w/h` 没设错；
- `frame` 尺寸、pickup 坐标空间都正确；
- 触控本身通（TRACKING_ID 事件能写入），不是触控限制；
- `input tap 712 343` 用画面坐标能直接点中弹窗按钮，证明 **input 命令的坐标就是画面坐标，系统旋转层是好的**——只有 sendevent 绕过了它、必须自己算，而自己算错了。

## 修复：改用 `input motionevent`（逻辑显示坐标）

本机 Android 15（SDK 35），支持 `input motionevent DOWN|MOVE|UP x y`。它传的是**逻辑显示坐标**，与截图/游戏画面一致（1920x1080），由 Android InputFlinger 自动旋转到物理触屏——**不需要任何手算映射**，从根上消除镜像错位。

- 新增 `AdbMotionEventDevice`（`src/task/multi_touch.py`）：`game_to_touch()` 只做 2048x1152 → 1920x1080 等比缩放，x/y 不交换、不翻转；DOWN/MOVE/UP 走 motionevent。
- `RahaiBlocksTask._make_interaction()` 在 MuMu 下改用该设备；旋转仍走 v1.8.13 的键位映射键（真实键盘），与触屏拖拽互不干扰。
- 单指即可完成拖拽（旋转已独立交给键盘），不再依赖 sendevent 的双指能力。
- 保留 `MultiTouchDevice`（sendevent）作为兼容，但方块任务默认不再使用。
