# v1.5.1 · 修复全新安装装不全导致的启动失败

## 中文

### 问题现象

有用户反馈：装了新版本后 **ok-ww 启动不了**，一直报错「没有 adb」，去 ok 安装目录里输指令也 **找不到 .py 文件**。

### 根因：安装脚本装不全

仓库里有**两个**安装脚本，它们维护的文件清单**早就不同步**了：

| 脚本 | 安装文件数 | 定位 |
|---|---|---|
| `tools/install_to_local_app.py` | **15 个** | 旧版「补丁式」安装器（首装入口） |
| `restore.py` | **32 个** | 新版「覆盖层」安装器（更新后恢复用） |

`AGENT_INSTALL_PROMPT.md` 里让 Agent 执行的是 `install_to_local_app.py`，也就是**首装路径**。
而这个旧脚本的文件清单停留在 v1.0.x 时代，从 v1.3.0 起新增的文件它一个都不装，
**17 个关键文件被漏掉**，其中包括：

- `ok/device/DeviceManager.py` —— 设备管理，安卓/adb 相关代码全在这里
- `src/task/BaseWWTask.py` —— **所有任务类的基类**，几乎每个任务都依赖它
- `ok/device/capture_methods/nemu_ipc.py` —— MuMu 抓屏
- `src/task/NightmareNestTask.py` —��� 梦魇聚落任务
- `src/task/touch_mode.py`、`src/task/android_world.py`、`src/task/android_book.py` —— 安卓端适配
- `ok/util/window.py`、`ok/device/interaction_methods/keys.py` —— 窗口与按键
- 以及 `config.py`、`ok/core/mcp_server.py` 等

结果就是：**首装用户拿到的 ok-ww 是个半残状态**，任务注册不全、adb 逻辑缺失，
报错信息五花八门，看起来像是「环境有问题」「没装 adb」，其实是补丁没装全。

### 修复

**1. `tools/install_to_local_app.py` 改为复用 `restore.py` 的完整清单**

不再维护两份清单 —— 直接 `from restore import RELATIVE_FILES`，两个脚本永远一致。
同时把工坊离线缓存也复制到 `repo` 目录（之前只复制到 `working`），
避免官方更新时从 `repo` 把 `working` 覆盖回去。

改动后安装脚本的行为：

- 装齐**全部 32 个**定制文件到 `working` **和** `repo` 两处（之前只装 `working`，且只有 15 个）
- 安装前先校验仓库源文件是否齐全，缺文件直接报错并提示重新下载整个仓库
  （之前只下载单个文件会静默装不全）
- 目标目录不存在时，提示怎么带参数重跑
- 保持幂等，可重复执行

**2. `AGENT_INSTALL_PROMPT.md` 补充目录结构与排查清单**

针对用户实际踩的坑做了说明：

- **ok-ww 的源码不在安装根目录**：
  `%LOCALAPPDATA%/ok-ww/` 下只有 `ok-ww.exe`，一个 `.py` 都没有；
  真正的源码在 `data/apps/ok-ww/working/`（运行）和 `data/apps/ok-ww/repo/`（源码副本）两处。
  在根目录找 `.py` 必然找不到，这是正常的。
- **优先用 ok-ww 自带的 Python**（`data/apps/ok-ww/python/python.exe`）。
  系统 Python 通常没装 `adbutils`，跑脚本会报 `ModuleNotFoundError: adbutils`，
  **看起来就像「没有 adb」** —— 这是「报错没 adb」的另一个真实来源。
- 新增「用户报启动不了 / 报没 adb / 找不到 .py」时的五步排查顺序：
  1. 确认 `working/ok/device/DeviceManager.py` 与 `working/src/task/BaseWWTask.py` 是否存在
     —— 缺失就是旧版安装器装不全，改跑 `restore.py` 补齐
  2. 确认选的是「云游戏」设备类型 —— 选「安卓/本地模拟器」才会走 adb 通道
  3. 确认模拟器已启动、adb 端口可连（MuMu 默认 `127.0.0.1:16384`）
  4. 查 `working/logs/ok-script.log`，搜 `ERROR` / `adb_start_game` / `get_preferred_device returned None`
  5. 日志出现 `set ADBUTILS_ADB_PATH failed` 说明找不到 `adb.exe`，通常是 adbutils 没装全

### 关于「有没有 adb」

**云游戏用户完全不需要 adb**，也不受本次修复影响：

- `adb_start_game()` 只在 `do_start` 的**安卓设备分支**里调用
  （`preferred['device']` 为 `windows` / `browser` 时走的是别的分支）
- 实测在「设备完全连不上」的情况下，`adb_start_game()` **耗时 0.00 秒**并返回 `False`，
  不会阻塞启动、不会抛异常

### 验证

新增 `probe/test_install_full.py`（13 项）—— 构造一个**只有上游原版**的假安装目录，
跑安装脚本后校验：32 个文件全部到位（`working` + `repo`）、内容与仓库源哈希一致、
全部 `.py` 可编译、重复运行幂等、目录不存在时给出可读提示。**全绿**。

回归：`test_black_frame` 19 项、`test_book_opened` 3 项、`test_android_book` 5 项、
`test_touch_book` 14 项、`test_android_world` 10 项、`test_disconnect` 5 项、
`test_adb_start_game` 19 项、`test_travel_button_ocr` 5 项 —— **全绿**（共 93 项）。

## English

### Symptom

Users reported that after installing the new version **ok-ww would not start**, kept
complaining about "no adb", and that **no `.py` files could be found** when running
commands in the ok-ww installation directory.

### Root cause: the installer only installed part of the patch

The repository contains **two** installers, and their file lists had long since
drifted apart:

| Script | Files installed | Role |
|---|---|---|
| `tools/install_to_local_app.py` | **15** | Old "patch-style" installer (the first-install entry point) |
| `restore.py` | **32** | New "overlay" installer (used to restore after official updates) |

`AGENT_INSTALL_PROMPT.md` instructs the Agent to run `install_to_local_app.py`, i.e.
the **first-install path**. That script's file list was frozen at the v1.0.x era and
does not install a single file added since v1.3.0 — **17 key files were silently
skipped**, among them:

- `ok/device/DeviceManager.py` — device management, all the Android/adb code lives here
- `src/task/BaseWWTask.py` — the **base class of every task**, nearly all tasks depend on it
- `ok/device/capture_methods/nemu_ipc.py` — MuMu screen capture
- `src/task/NightmareNestTask.py` — the Nightmare Nest task
- `src/task/touch_mode.py`, `src/task/android_world.py`, `src/task/android_book.py` — Android adaptations
- `ok/util/window.py`, `ok/device/interaction_methods/keys.py` — windowing and key input
- plus `config.py`, `ok/core/mcp_server.py` and others

The result: **a first-time user ended up with a half-broken ok-ww** — tasks not
registered, adb logic missing, and error messages that look like "your environment is
wrong" or "adb is missing" when the truth is that the patch was never fully installed.

### The fix

**1. `tools/install_to_local_app.py` now reuses the full list from `restore.py`**

There is no longer a second list to maintain — it does `from restore import
RELATIVE_FILES`, so the two scripts can never drift apart again. The offline workshop
cache is now copied into the `repo` directory as well (previously only into
`working`), so an official update cannot restore `working` from an untouched `repo`.

The installer now:

- installs **all 32** custom files into **both** `working` and `repo`
  (previously: 15 files, `working` only)
- verifies up front that all source files are present in the repository, and fails
  loudly with "please re-download the whole repository" if any are missing
  (downloading a single file used to fail silently and partially)
- prints how to pass an explicit path when the target directory is not found
- stays idempotent and can be re-run safely

**2. `AGENT_INSTALL_PROMPT.md` now documents the directory layout and a triage list**

It covers the exact pitfalls users hit:

- **ok-ww's source is not in the installation root**: `%LOCALAPPDATA%/ok-ww/` contains
  only `ok-ww.exe` and not a single `.py`; the real source lives in
  `data/apps/ok-ww/working/` (the running copy) and `data/apps/ok-ww/repo/` (the source
  copy). Looking for `.py` files in the root will never find them — that is normal.
- **Prefer ok-ww's bundled Python** (`data/apps/ok-ww/python/python.exe`). A system
  Python usually has no `adbutils`, and running the scripts then raises
  `ModuleNotFoundError: adbutils`, which **looks exactly like "adb is missing"** — the
  other real source of the "no adb" complaint.
- A new five-step triage order for "will not start / says no adb / cannot find .py":
  1. Check that `working/ok/device/DeviceManager.py` and `working/src/task/BaseWWTask.py`
     exist — if missing, the old installer was used; run `restore.py` to install all 32
  2. Check that the **云游戏** (cloud game) device type is selected — only the
     Android/emulator type uses the adb channel
  3. Check that the emulator is running and the adb port is reachable
     (MuMu defaults to `127.0.0.1:16384`)
  4. Read `working/logs/ok-script.log` and search for `ERROR` / `adb_start_game` /
     `get_preferred_device returned None`
  5. If the log shows `set ADBUTILS_ADB_PATH failed`, `adb.exe` could not be found —
     usually because adbutils is not installed properly

### About "some people have no adb"

**Cloud game users need no adb at all** and are unaffected by this fix:

- `adb_start_game()` is called **only** in the Android device branch of `do_start`
  (`preferred['device']` values `windows` / `browser` take different branches)
- Measured with a completely unreachable device, `adb_start_game()` returns `False`
  in **0.00 seconds** — it never blocks startup and never raises

### Validation

New `probe/test_install_full.py` (13 assertions) builds a fake installation directory
containing **only the pristine upstream files**, runs the installer and then verifies
that all 32 files are in place (in both `working` and `repo`), that their contents
match the repository sources by hash, that every `.py` compiles, that a second run is
idempotent, and that a missing target directory produces a readable hint — **all green**.

Regression: `test_black_frame` 19, `test_book_opened` 3, `test_android_book` 5,
`test_touch_book` 14, `test_android_world` 10, `test_disconnect` 5,
`test_adb_start_game` 19, `test_travel_button_ocr` 5 — **all green** (93 assertions).
