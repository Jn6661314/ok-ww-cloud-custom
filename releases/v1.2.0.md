# v1.2.0 · 云战斗工坊修复 / 无怪物自动退出 / Win10 云鸣潮 / 触屏键位补全

## 中文

### 云鸣潮战斗不使用工坊参数 / 乱切人（两个问题同源）

云鸣潮抓的是 WebRTC 视频流（H.264 + 4:2:0 色度抽稀），角色头像/文字模板与协奏环颜色识别都会抖动。而工坊队伍代码的接入逻辑对识别结果有"全有或全无"的强依赖，某一帧认错就把整队工坊代码丢掉，角色类型退回默认 `MAIN_DPS`、切人优先级走内置默认，于是表现为"工坊参数没生效 + 乱切人"。

- **工坊队伍代码每轮被退回内置类（核心 bug）**：工坊队伍代码是内置角色类的"兄弟"类（同名、都直接继承 `BaseChar`，不是内置类的子类），`CharFactory.get_char_by_pos` 里的 `isinstance(old_char, cls)` 对工坊实例恒为 False，导致每轮识别都把工坊实例用内置类重建，工坊自定义战斗逻辑/切人优先级全部丢失。改为按类名判断（`old_char.name != cls.__name__` 才重建），自定义类同名即保留，真正换角色才重建。
- **单槽位识别失败导致整队工坊失效**：`apply_team_char_classes` 原来是"全有或全无"——只要有一个角色认不出（`char_name='unknown'` / 人数≠3）就整体跳过，另外两个认出的角色也拿不到工坊代码。现在在 task 上缓存每个槽位上一轮的身份 `{index: (canonical_name, builtin_cls)}`，某帧认不出时用缓存身份补全，工坊代码仍应用到全队；缓存是 per-task 的，云多账号各实例互不干扰。
- **协奏环颜色在云流下失准**：`con_colors` 每个通道区间仅约 30 宽，4:2:0 压缩后颜色偏移导致协奏值算错 → intro 预判错 → 乱切人。云浏览器模式下对每个通道区间向外放宽 `CLOUD_CON_COLOR_TOLERANCE`（默认 10，可在 `BaseCombatTask.py` 顶部调整）用于环颜色统计与属性索引推断；本地客户端不走此分支，识别行为零变化。
- 验证：`tests/TestCloudCombatFixes.py` 4 项单测（工坊类保活、缓存补全、颜色容差仅云模式生效）全部通过；原有 `TestCustomCharLoader.py` 26 项无回归。

### 无怪物时自动退出战斗

- **无怪物看门狗**（`src/combat/CombatCheck.py`）：新增无怪物看门狗，连续 2 秒既没有锁定目标、也看不到血条即判定怪物已死亡/消失并退出战斗。血条因云游戏压缩闪烁时不会无限续命；深渊挑战强制战斗窗口与大招动画期间不触发，避免误伤。
- **大招标志残留**（`src/task/BaseCombatTask.py`）：`send_key_and_wait_animation` 超时时 `_in_liberation` 可能仍为 True，导致 `in_combat()` 永远返回 True、战斗退不出去。超时处补上清理。

### MuMu 触屏模式的 esc 返回键

- **问题**：ADB/MuMu 触屏操作模式下，业务代码里大量 `send_key('esc')`（返回/关闭界面）被映射成 `KEYCODE_ESCAPE`，鸣潮手游不响应该键，导致日常任务卡在菜单、无法返回。
- **修复**（`ok/device/interaction_methods/keys.py`）：`ADB_KEY_MAP['esc']` 由 `KEYCODE_ESCAPE` 改为 `KEYCODE_BACK`（安卓返回键）。该映射表仅 ADB 交互使用，PC（PostMessage/Pynput）与云游戏浏览器模式均不受影响。
- **验证**：语法检查通过；映射断言 `ADB esc == KEYCODE_BACK` 且 `PC vk ESC == 27`（未改动）通过。

### ADB 触屏键位表补全（A-Z / 0-9 / 反引号）

- **根因**：`ADB_KEY_MAP` 只定义了 esc/enter/space/方向键/修饰键等，`src/` 里用到的 8 个字母键（f/m/z/w/r/d/c/a）没有映射，在 ADB 交互下被原样透传成 `input keyevent f` 这类非法命令，安卓不认识小写键名，游戏收不到任何事件——这才是日常任务在 MuMu 触屏模式下大面积失效的主因，比 esc 问题更严重。
- **修复**（`ok/device/interaction_methods/keys.py`）：补全 a-z → `KEYCODE_A`..`KEYCODE_Z`、0-9 → `KEYCODE_0`..`KEYCODE_9`；反引号 `` ` ``/grave/backtick → `KEYCODE_GRAVE`。此表仅 ADB 交互使用，PC 与云游戏浏览器模式不受影响。
- **验证**：代码用到的 13 个键现全部映射为合法 keyevent；`ADB['f']==KEYCODE_F` / `ADB['esc']==KEYCODE_BACK` / `ADB['`']==KEYCODE_GRAVE` 断言通过；PC 端 `vk_key_dict['ESC']==27` 未改动。

## English

### Cloud combat ignoring workshop team code / erratic character switching (one shared root cause)

The cloud client captures a WebRTC video stream (H.264 with 4:2:0 chroma subsampling), so character portrait/text templates and concerto-ring colour detection both jitter. The workshop team-code integration, however, has an all-or-nothing dependency on recognition results: a single misrecognized frame throws away the whole team's workshop code, the character type falls back to the built-in `MAIN_DPS`, and the switch priority uses the built-in defaults — which shows up as "workshop parameters not applied" plus "erratic character switching".

- **Workshop team codes were downgraded to built-in classes every round (core bug)**: a workshop team code is a "sibling" class of the built-in character class (same name, both directly inheriting `BaseChar`, not a subclass of the built-in one), so the `isinstance(old_char, cls)` check in `CharFactory.get_char_by_pos` was always False for workshop instances. Every recognition round therefore rebuilt the workshop instance with the built-in class, losing all workshop-specific combat logic and switch priorities. The check is now done by class name (rebuild only when `old_char.name != cls.__name__`), so a custom class with a matching name is preserved and only a genuine character change triggers a rebuild.
- **One failed slot disabled the whole team's workshop code**: `apply_team_char_classes` used to be all-or-nothing — if any character was unrecognized (`char_name='unknown'` / team size ≠ 3) the entire team was skipped, so the two recognized characters lost their workshop code too. The task now caches each slot's identity from the previous round (`{index: (canonical_name, builtin_cls)}`) and fills in from that cache when a frame fails, so workshop codes still apply to the whole team. The cache is per-task, so cloud multi-account instances do not interfere with each other.
- **Concerto ring colours are inaccurate in the cloud stream**: each `con_colors` channel interval is only about 30 wide, and 4:2:0 compression shifts the colour so the concerto value is computed wrong → wrong intro prediction → erratic switching. In cloud browser mode every channel interval is widened by `CLOUD_CON_COLOR_TOLERANCE` (default 10, tunable at the top of `BaseCombatTask.py`) for ring-colour statistics and attribute-index inference. The local client does not take this branch, so its recognition behaviour is unchanged.
- Validation: 4 unit tests in `tests/TestCloudCombatFixes.py` (workshop class survival, cache-based completion, colour tolerance only in cloud mode) all pass; the existing 26 `TestCustomCharLoader.py` tests show no regression.

### Auto-exit combat when there are no monsters

- **No-monster watchdog** (`src/combat/CombatCheck.py`): a new watchdog judges that the monster is dead/gone and exits combat when there is neither a locked target nor a visible HP bar for 2 consecutive seconds. A flickering HP bar due to cloud compression no longer keeps the task alive forever; it does not trigger during the abyss challenge's forced combat window or during ultimate animations, avoiding false positives.
- **Stale ultimate flag** (`src/task/BaseCombatTask.py`): when `send_key_and_wait_animation` times out, `_in_liberation` could stay True, making `in_combat()` return True forever so combat could never be exited. The flag is now cleared on timeout.

### Win10 cloud support

- The WGC availability gate used Win11's "borderless" build 20348, but WGC has been available since Win10 2004 (19041); the check now uses 19041 and keeps the COM component runtime probe.
- The "remove the yellow capture border" setting is now attempted on Win10 as well, with proper fallback handling.
- The device label is updated to "requires Win10 2004+ or Win11".
- Validation: simulated 19041 / 19045 / 22621, all usable in cloud mode; syntax check passes; targeted watchdog tests pass.

### MuMu touch mode: the `esc` back key

- **Problem**: in ADB/MuMu touch mode, the many `send_key('esc')` calls in the business code (back / close UI) were mapped to `KEYCODE_ESCAPE`, which the Wuthering Waves mobile client ignores — daily tasks got stuck in menus and could not go back.
- **Fix** (`ok/device/interaction_methods/keys.py`): `ADB_KEY_MAP['esc']` changed from `KEYCODE_ESCAPE` to `KEYCODE_BACK` (the Android back key). This map is only used for ADB interaction; PC (PostMessage/Pynput) and cloud browser mode are unaffected.
- **Validation**: syntax check passes; the assertions `ADB esc == KEYCODE_BACK` and `PC vk ESC == 27` (unchanged) pass.

### Complete the ADB touch key map (A-Z / 0-9 / backtick)

- **Root cause**: `ADB_KEY_MAP` only defined esc/enter/space/arrow/modifier keys. The 8 letter keys used in `src/` (f/m/z/w/r/d/c/a) had no mapping and were passed through verbatim as illegal commands like `input keyevent f`; Android does not know lowercase key names, so the game received no events at all — this, not the esc problem, was the main reason daily tasks largely failed in MuMu touch mode.
- **Fix** (`ok/device/interaction_methods/keys.py`): added a-z → `KEYCODE_A`..`KEYCODE_Z` and 0-9 → `KEYCODE_0`..`KEYCODE_9`; backtick `` ` ``/grave/backtick → `KEYCODE_GRAVE`. This map is only used for ADB interaction; PC and cloud browser mode are unaffected.
- **Validation**: all 13 keys used by the code now map to legal keyevents; the assertions `ADB['f']==KEYCODE_F` / `ADB['esc']==KEYCODE_BACK` / `ADB['`']==KEYCODE_GRAVE` pass; the PC-side `vk_key_dict['ESC']==27` is unchanged.
