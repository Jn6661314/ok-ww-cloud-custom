# v1.5.7 · 修复 MuMu 手游端“锁定也不打 / 角色动都不动” / Fix MuMu mobile combat doing nothing even after target lock

## 中文

### 问题现象

前面 v1.5.2～v1.5.6 已经依次修掉了当前角色下标、锁敌判定、切人循环、掉线弹窗和重击长按崩溃，
但 MuMu 手游端仍然表现为：

- 敌人血条就在屏幕上，脚本也在战斗循环里，但角色**一动不动**、怪不掉血；
- 锁敌必须用户手动按 `Y`；脚本自己 `send_key('y')` 没有反应；
- 技能键发出去没有动画，日志里反复出现 `click_liberation ... timeout`；
- 日志同时出现过 `'ADBInteraction' object has no attribute 'mouse_down'`，说明实际交互层并不是配置里写的 Pynput。

### 根因：实际生效的是 ADBInteraction，而手游只认模拟器键位映射

`configs/devices.json` 里虽然写了 `interaction: Pynput`，但运行配置是 `capture: "ipc"`。
`DeviceManager.do_start()` 中“用窗口键鼠交互覆盖 ADB”的条件要求 `capture == 'windows'`，
ipc 场景下条件不成立，最终仍回退到 `ADBInteraction`（日志已实锤）。

这会同时打断两条关键输入链路：

1. **键盘链路**：`ADBInteraction.send_key()` 发的是 `input keyevent KEYCODE_*`，属于安卓系统层按键；
   而 MuMu 手游依赖的是模拟器把**真实 Windows 键盘事件**转换成触摸的“键位映射”。
   所以手动按 `Y` 能锁敌，脚本发 keyevent 却毫无反应，`e/q/r` 技能键也就一直 timeout。
2. **普攻链路**：PC 端鼠标左键点屏幕任意位置就是普攻；手游端必须点右下角圆形“攻击”按钮。
   `BaseWWTask.click()` 无坐标时默认点 `(0.5, 0.5)`，在手游里落在角色/空地上，
   表现就是“角色动都不动”。

另外，Pynput 真实键盘只会送到**前台窗口**，所以只补键盘事件还不够，发送前必须把 MuMu 窗口切到前台。

### 修复（全部在 BaseWWTask 覆盖层，PC / 云游戏 / 真机行为不变）

- **手游普攻点在攻击按钮上**：安卓战斗中无坐标的 `click()` / `mouse_down()` 改为点右下角
  `TOUCH_ATTACK_BUTTON = (0.80, 0.775)`（按执行器 1920×1080 frame 换算，约 `(1536, 837)`），
  不再点屏幕中心；非战斗、显式坐标、PC / 云游戏路径保持原样。
- **模拟器叠加真实键盘并先切前台**：当且仅当 `is_adb()` 为真、设备管理器有 `hwnd_window`、
  且当前交互层确实是 `ADBInteraction` 时：
  - 先用 `hwnd_window.is_foreground()` / `bring_to_front()` 确保 MuMu 在前台；
  - 再用 Pynput 发真实 `press/release`，触发模拟器键位映射（`Y` 锁敌、`e/q/r` 技能、`w/a/s/d` 走位）；
  - 前台仍切换失败时跳过真实键盘，避免把按键发到别的窗口；
  - 原 `super().send_key()` 的 ADB keyevent 通道保留，真机没有窗口句柄时行为完全不变。
- **长按走位同步补齐**：`send_key_down()` / `send_key_up()` 在模拟器上同样用 Pynput 按下/抬起，
  且绝不回落到 `ADBInteraction` 上不存在的同名方法（避免 `AttributeError` 再次打断战斗）；
  PC / 云游戏继续走上游实现。

### 验证

- 新增 `tests/TestAndroidKeymapCombat.py`：15 项全绿，覆盖攻击按钮坐标、非战斗仍点中心、
  nemu 长按、前台切换、真实键盘按下/抬起、非前台拒绝发送、不回落到不存在的 ADB down/up、
  真机/PC/非 ADB 交互层不生效。
- 回归全绿：`TestAndroidCombatFix` 13、`TestAndroidDisconnect` 7、`TestAndroidMouseHold` 8、
  `TestAndroidTargetKey` 13、`TestCloudCombatFixes` 4。
- `restore.py` 已部署到 working + repo；仓库源、working、repo 三处 `BaseWWTask.py` 哈希一致，编译通过。

### 建议验证方式

1. 确认 MuMu 里已配置键位映射，`Y` = 锁敌，`e/q/r` = 共鸣技能/共鸣解放，`w/a/s/d` = 移动。
2. 启动 ok-ww，选安卓/MuMu 设备，跑一个含战斗的日常任务。
3. 观察 10～20 秒：角色应自动锁敌并出现普攻/技能动画；日志不再反复 `click_liberation timeout`。
4. 注意：本版本会在需要按键时把 MuMu 窗口切到前台，运行期间尽量不要抢焦点。

## English

### Symptom

v1.5.2–v1.5.6 fixed the current-character index, target detection, character switching,
disconnect dialog and heavy-attack crash respectively. MuMu mobile combat still showed:

- The enemy health bar was visible and the combat loop was running, but the character **never moved**
  and the enemy never lost HP;
- Target lock only worked when the user manually pressed `Y`; the script's `send_key('y')` did nothing;
- Skill keys produced no animation and logs repeatedly showed `click_liberation ... timeout`;
- Logs also contained `'ADBInteraction' object has no attribute 'mouse_down'`, proving the active
  interaction layer was not the configured Pynput one.

### Root cause: ADBInteraction was active, while the mobile game only accepts the emulator keymap

`configs/devices.json` had `interaction: Pynput`, but the runtime capture was `ipc`.
In `DeviceManager.do_start()`, the override that replaces ADB with a window keyboard/mouse interaction
requires `capture == 'windows'`. With `ipc` it never applied, so the manager fell back to
`ADBInteraction` (confirmed by the logs).

That broke two input paths at once:

1. **Keyboard**: `ADBInteraction.send_key()` sends `input keyevent KEYCODE_*`, i.e. Android system key
   events. The mobile game instead expects **real Windows keyboard events** converted into touches by
   the emulator keymap. That is why manual `Y` locked on but scripted key events did nothing, and why
   `e/q/r` kept timing out.
2. **Normal attack**: on PC, left-clicking anywhere attacks; on mobile, only the round attack button in
   the lower-right corner does. `BaseWWTask.click()` with no coordinates clicked `(0.5, 0.5)`, which on
   mobile lands on the character/empty ground — exactly "the character does nothing".

Also, Pynput delivers keys only to the **foreground** window, so bringing MuMu to the front is required
before sending real keys.

### Fix (BaseWWTask override; PC / cloud / real-device behavior unchanged)

- **Attack button for mobile**: when `is_adb()` and `_in_combat`, coordinate-less `click()` /
  `mouse_down()` now target `TOUCH_ATTACK_BUTTON = (0.80, 0.775)` in the 1920x1080 executor frame
  (about `(1536, 837)`) instead of screen center. Non-combat, explicit coordinates, PC and cloud paths
  are untouched.
- **Real keyboard with focus, emulator only**: only when `is_adb()` is true, the device manager has an
  `hwnd_window`, and the active interaction is really `ADBInteraction`:
  - ensure MuMu is foreground via `is_foreground()` / `bring_to_front()`;
  - send real `press/release` with Pynput to trigger the emulator keymap (`Y` lock, `e/q/r` skills,
    `w/a/s/d` movement);
  - skip real keys if the window still cannot be focused, so keystrokes never leak to another app;
  - keep the original `super().send_key()` ADB keyevent path; real devices without a window handle are
    unchanged.
- **Held movement**: `send_key_down()` / `send_key_up()` use Pynput on emulators as well and never fall
  back to the missing `ADBInteraction` methods (which would raise `AttributeError` again); PC/cloud still
  delegate to the upstream implementation.

### Verification

- New `tests/TestAndroidKeymapCombat.py`: 15 tests all green (attack-button coords, non-combat center
  fallback, nemu hold, foreground switch, real key press/release, non-foreground rejection, no fallback to
  missing ADB down/up, no effect on real device / PC / non-ADB interaction).
- Regression all green: `TestAndroidCombatFix` 13, `TestAndroidDisconnect` 7, `TestAndroidMouseHold` 8,
  `TestAndroidTargetKey` 13, `TestCloudCombatFixes` 4.
- Deployed to working + repo via `restore.py`; `BaseWWTask.py` hashes match across source, working and
  repo, and compilation passes.

### Suggested check

1. Confirm MuMu's keymap is configured: `Y` = target lock, `e/q/r` = skills/liberation, `w/a/s/d` = move.
2. Start ok-ww, select the Android/MuMu device, and run a daily task that includes combat.
3. Within 10–20 seconds the character should auto-lock and show attack/skill animations; logs should stop
   repeating `click_liberation timeout`.
4. Note: this version brings MuMu to the foreground when sending keys — avoid taking focus while it runs.
