# v1.8.2 · 修掉「本地版本显示 3.8.14」

## 现象

代码早就是官方 **v3.8.15** 基线，但启动器（ok-ww.exe）界面上的版本号还写着 **3.8.14**。

三条证据说明代码确实是 3.8.15：

- `working/config.py` 第 11 行：`version = "v3.8.15"`
- 启动日志：`ok:ok-script init v3.8.15`
- 应用内「关于」页：`UpdateCard:initialized current_version='v3.8.15'`

## 为什么

ok-ww 有**两个**版本号来源，各管一段：

| 来源 | 谁在用 | 修复前的值 |
| --- | --- | --- |
| `working/config.py` 的 `version` | 应用内「关于」页、更新卡片、日志 | `v3.8.15` ✅ |
| `data/apps/ok-ww/app.json` 的 `current_version` | **启动器**（ok-ww.exe）窗口标题/版本行，以及"有没有新版本"的判断 | `v3.8.14` ❌ |

`app.json` 是 pyappify 的应用清单，`current_version` 记录"已安装版本"。它是当初装 3.8.14 时写下的，
而 `restore.py` 只覆盖代码文件、从没动过它，所以一直是旧值。启动器通过环境变量把它传给应用：

```
ok:pyappify  app_version:v3.8.14, app_profile:China, pyappify_version:1.2.3
```

## 危害（不只是显示错）

`app.json` 里 `available_versions` 的第一个就是 `v3.8.15`。启动器认为"当前 3.8.14 → 可更新到 3.8.15"，
于是**会允许甚至提示更新**。一旦点了更新：

- 官方 v3.8.15 的代码会覆盖 `working` 和 `repo`；
- 云鸣潮多账号、MuMu/安卓、拉海洛方块的无尽模式、远控窗口支持**全部消失**；
- 你得重新跑 `restore.py` 才能回来。

## 修复

`restore.py` 新增 `sync_app_version()`，每次部署后自动把
`app.json.current_version` 对齐到 `config.py` 的 `version`：

- 版本不同 → 先备份成 `app.json.<时间戳>.bak`，再改（其余字段原样保留）；
- 版本相同 → 不动文件，不打多余备份；
- 找不到 `app.json` / JSON 损坏 / 顶层不是对象 → 打印原因后安全跳过，不让部署失败。

当前已同步：`app.json.current_version` = **v3.8.15**。

这样启动器认为"已是最新"，不会再提示更新到 3.8.15，也就不会误覆盖定制。

## 测试

新增 `tests/TestAppVersionSync.py` **9 项**：

- 读取仓库 `config.py` 的版本，且格式是 `vX.Y.Z`（启动器按数字比版本，`dev` 之类会一直提示更新）；
- 版本不同时改写且其余字段不变；
- 改写前生成备份，备份里是旧值；
- 版本相同时文件一字不动、不产生备份；
- `--no-backup` 生效；
- 缺 `app.json` / 坏 JSON / 非对象 JSON 都不抛异常、不破坏原文件。

全量 **226 项测试通过**。

## 升级

照常 `python restore.py`，然后重启 ok-ww。启动器窗口会显示 **v3.8.15**。

> 注意：启动器的版本判断依赖 `app.json`，所以**每次部署完都请用 `restore.py`**，
> 不要手动只拷几个 `.py` 文件 —— 否则版本号又会和代码错位。

# v1.8.2 · Fix "local version still shows 3.8.14"

## Symptom

The code base has been on official **v3.8.15** for a while, yet the launcher (ok-ww.exe) still
displays **3.8.14**.

Proof the code is 3.8.15:

- `working/config.py` line 11: `version = "v3.8.15"`
- startup log: `ok:ok-script init v3.8.15`
- in-app About page: `UpdateCard:initialized current_version='v3.8.15'`

## Why

ok-ww has **two** version sources:

| Source | Used by | Value before this fix |
| --- | --- | --- |
| `version` in `working/config.py` | in-app About page, update card, logs | `v3.8.15` ✅ |
| `current_version` in `data/apps/ok-ww/app.json` | the **launcher** (window title / version row, and the "is an update available" check) | `v3.8.14` ❌ |

`app.json` is pyappify's app manifest; `current_version` is the recorded installed version, written
back when 3.8.14 was installed. `restore.py` only copied code files and never touched it. The launcher
passes it into the app via `PYAPPIFY_APP_VERSION`:

```
ok:pyappify  app_version:v3.8.14, app_profile:China, pyappify_version:1.2.3
```

## Why it matters (more than cosmetics)

`available_versions[0]` is `v3.8.15`, so the launcher believes "3.8.14 → can update to 3.8.15".
If the user clicks update, official code overwrites `working` and `repo` and **every customization
disappears** (cloud multi-account, MuMu/Android, Rahai endless mode, remote-window support).

## Fix

`restore.py` now has `sync_app_version()`, run after each deployment:

- different version → back up to `app.json.<timestamp>.bak`, then rewrite `current_version`
  (all other fields preserved);
- same version → leave the file untouched, no redundant backup;
- missing / malformed / non-object JSON → print the reason and skip safely instead of failing.

`app.json.current_version` is now **v3.8.15**, so the launcher shows the right version and no longer
offers an update that would wipe the customizations.

## Tests

`tests/TestAppVersionSync.py` adds **9 tests** (rewrite, backup, no-op when aligned, `--no-backup`,
missing file, broken JSON, non-object JSON, version format). **226 tests pass** overall.

## Upgrade

Run `python restore.py` as usual, then restart ok-ww. The launcher will show **v3.8.15**.

> Always deploy with `restore.py` rather than copying a few `.py` files by hand — otherwise the
> launcher version and the code version drift apart again.
