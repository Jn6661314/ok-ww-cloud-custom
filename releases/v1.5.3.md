# v1.5.3 · 修复 MuMu 手动锁定后仍不战斗 / Fix MuMu still not fighting after manual target lock

## 中文

### 问题现象

v1.5.2 修复了「进战斗即崩溃」之后，MuMu 上又出现新问题：脚本能识别角色、也能看到敌人在打，
但**自己不出招**。即使玩家手动在模拟器里锁定了敌人，脚本依然不动。日志里反复刷：

```
CombatCheck:target lost try retarget 10
AutoCombatTask:选择目标失败!请关闭显卡滤镜和锐化!
```

但画面上敌人和血条都清晰可见，并不是真的「没有目标」或「显卡滤镜」问题。PC 客户端与云游戏不受影响。

### 根因：手游 UI 与 PC 的战斗判定完全不同

抓了失败瞬间的真实截图（1920×1080）分析后发现两个致命错配：

1. **锁定图标判定失效**：`has_target()` 找的是 PC 端的锁定图标模板（`has_target_3840x2160`）。
   但 MuMu 是**手游 UI**，根本没有那个骷髅准星图标——全屏模板匹配最高分只有 0.63 且位置在屏幕顶端，
   是误匹配。于是 `has_target()` 恒为假，`target_enemy()` 每 10 秒重锁一次，永远进不了攻击循环。
   手动锁定也没用，因为脚本压根不看游戏里真正的锁定状态。

2. **血条检测漏判**：手游敌人是**头顶红色血条**（带抗锯齿渐变，红色填充率约 0.8~0.9）。
   PC 用的颜色检测阈值是 `0.95`，把这些血条全部过滤掉了，`check_health_bar()` 也是假。
   实测把阈值放宽到 `0.8` 后，能稳定识别出 4 个敌人血条（如 `x=583,y=327,w=168,h=10`）。

3. **锁敌键错误**：战斗锁敌统一走鼠标中键 `middle_click()`，但 MuMu/ADB 通道里中键不触发游戏锁敌；
   正确方式是按 **Y 键**（模拟器键位映射里的锁定目标键）。

### 修复

核心思路：安卓端的「有敌人」判定改用手游真正存在的视觉特征，锁敌改用模拟器支持的按键。
PC / 云游戏分支完全不动。

**1. `CombatCheck.has_target()`：安卓端用血条代替锁定图标**

```python
if self.is_adb():
    # 手游 UI 没有 PC 锁定图标, 有敌人头顶血条即等价于有可战斗目标
    return self.check_health_bar()
```

**2. `CombatCheck.has_health_bar()`：安卓端放宽血条阈值**

- 检测阈值从 `0.95` 放宽到 `0.8`（实测手游血条填充率约 0.8~0.9）。
- 额外要求血条是横向条形且宽度达标，排除伤害数字和技能特效误判。
- PC 端仍用 `0.95`，云游戏仍用 `CLOUD_HEALTH_BAR_FILL`，行为不变。

**3. 新增 `tap_target()`：统一锁敌按键**

- 安卓端：`send_key('y')`（Y 键锁定目标）。
- PC / 云游戏：`middle_click()`（鼠标中键，与原行为一致）。
- 替换了所有战斗锁敌调用点：`do_check_in_combat()`、`target_enemy()` 的即时锁敌与重试循环、
  `BaseCombatTask.wait_combat()`。

### 验证

- 用失败瞬间的真实战斗截图做像素级验证：修复后 adb 端 `has_health_bar` / `has_target` /
  `target_visible` 全部为 `True`；同一张截图在 PC 分支仍判为无目标，确认分支隔离。
- 新增 `tests/TestAndroidTargetKey.py`（10 项）全绿。
- 回归 `TestAndroidCombatFix`（13 项）、`TestCloudCombatFixes`（4 项）全绿。
- 修改文件都在 `restore.py` 32 文件清单内，三处（仓库 / working / repo）哈希一致、编译通过。

## English

### Symptom

After v1.5.2 fixed the "crash on entering combat" issue, a new problem appeared on MuMu:
the script recognized the characters and could see enemies fighting, but **never attacked by itself**.
Even after the player manually locked an enemy in the emulator, the script stayed idle. The log kept repeating:

```
CombatCheck:target lost try retarget 10
AutoCombatTask:选择目标失败!请关闭显卡滤镜和锐化!
```

Yet enemies and their health bars were clearly visible — there was no real "no target" or GPU-filter issue.
The PC client and cloud gaming were unaffected.

### Root cause: mobile UI uses completely different combat detection

Analyzing a real screenshot captured at the moment of failure (1920×1080) revealed two fatal mismatches:

1. **Target-lock detection failed**: `has_target()` looked for the PC lock-on icon template
   (`has_target_3840x2160`). But MuMu runs the **mobile UI**, which has no such crosshair/skull icon —
   the best full-screen template match was only 0.63 and landed at the top edge of the screen (a false positive).
   So `has_target()` was always false, `target_enemy()` retried every 10 seconds, and the attack loop
   was never entered. Manual locking did not help because the script never checked the game's real lock state.

2. **Health-bar detection missed mobile bars**: mobile enemies show a **red health bar above their head**
   (with anti-aliasing/gradient, red fill ratio ~0.8–0.9). The PC color threshold of `0.95` filtered all of
   them out, so `check_health_bar()` was also false. Lowering the threshold to `0.8` reliably detected
   four enemy bars (e.g. `x=583,y=327,w=168,h=10`).

3. **Wrong target-lock key**: all target locking used the mouse middle button `middle_click()`, which does not
   trigger lock-on through the MuMu/ADB channel. The correct key is **Y** (the emulator's lock-target binding).

### Fix

For Android, detect "an enemy exists" using visual features that actually exist in the mobile UI,
and use a key the emulator supports. PC / cloud-gaming branches are untouched.

**1. `CombatCheck.has_target()`: use health bars instead of the lock icon on Android**

```python
if self.is_adb():
    # Mobile UI has no PC lock icon; an enemy health bar means a targetable enemy
    return self.check_health_bar()
```

**2. `CombatCheck.has_health_bar()`: relax the threshold on Android**

- Threshold relaxed from `0.95` to `0.8` (measured mobile bar fill ratio ~0.8–0.9).
- Additionally requires a horizontal bar of sufficient width, excluding damage numbers and skill effects.
- PC still uses `0.95`, cloud still uses `CLOUD_HEALTH_BAR_FILL` — no behavior change.

**3. New `tap_target()`: unified target-lock key**

- Android: `send_key('y')` (Y key locks the target).
- PC / cloud: `middle_click()` (middle mouse button, same as before).
- Replaced every combat lock-on call site: `do_check_in_combat()`, both immediate and retry paths in
  `target_enemy()`, and `BaseCombatTask.wait_combat()`.

### Verification

- Pixel-level verification against the real failure screenshot: after the fix, Android `has_health_bar` /
  `has_target` / `target_visible` are all `True`; the same screenshot on the PC branch still reports no target,
  confirming branch isolation.
- New `tests/TestAndroidTargetKey.py` (10 tests) all passing.
- Regressions `TestAndroidCombatFix` (13 tests) and `TestCloudCombatFixes` (4 tests) all passing.
- All modified files are in the `restore.py` 32-file manifest; hashes match across repo / working / install
  directories and compilation succeeds.
