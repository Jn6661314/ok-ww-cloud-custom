# v1.8.4 · 修复启动即崩（`MuMu/安卓 Config` 改名漏改引用）

## 现象

23:56 打开 ok-ww，连试三次都在启动阶段退出，日志：

```
ERROR MainThread ok:__init__ error Traceback (most recent call last):
  ...
  File "src\task\BaseWWTask.py", line 123, in __init__
    self.android_config = self.get_global_config('MuMu/安卓 Config')
  File "ok\util\GlobalConfig.py", line 354, in get_config
    raise RuntimeError(f'Can not find global config {option}')
RuntimeError: Can not find global config MuMu/安卓 Config
```

任务管理器在实例化 `AutoCombatTask` → `BaseCombatTask` → `CombatCheck` → `BaseWWTask` 时，
`BaseWWTask.__init__` 要读安卓编队配置，但读的名字在配置表里不存在，于是整条初始化链崩掉，
应用直接 `quit app`。

## 根因

v1.8.1 把全局配置 `MuMu/安卓 Config` 改名为 **`MuMu 安卓 Config`**（配置名不能含 `/`，
否则框架会按 `configs/<名称>.json` 落盘、斜杠变子目录），但只改了 `config.py` 的注册处，
**漏改了 `src/task/BaseWWTask.py:123` 的读取处**。

- 注册处：`ConfigOption('MuMu 安卓 Config', ...)`
- 读取处：`get_global_config('MuMu/安卓 Config')` ← 旧名，永远匹配不到

任何任务初始化都会走 `BaseWWTask.__init__`，所以不是"MuMu 功能异常"，而是**整个程序起不来**。
v1.8.1 部署后一直没启动过 ok-ww，直到 23:56 首次启动才暴露。

## 修复

1. `src/task/BaseWWTask.py:123` 改为 `get_global_config('MuMu 安卓 Config')`；
2. 同文件与 `src/task/BaseCombatTask.py` 里指代该配置的注释一并统一；
3. 新增 `tests/TestGlobalConfigRefs.py`（**4 项**，纯 AST 静态扫描，不导入 config.py，
   因此不依赖 cv2 / PySide6）：

   - `config.py` 里所有 `ConfigOption('<名>')` 的注册名能被正确解析（先自检解析器不空转）；
   - 注册名不得含 `/`（防配置落进子目录）；
   - `src/` 下每个 `get_global_config('<名>')` 的字面量**必须**在注册名里 —— 正是这次漏改的检查；
   - `src/` 下 `*_CONFIG_NAME` 常量（如 `stream_window.STREAM_CONFIG_NAME`）也必须在注册名里。

全量 **243 项测试通过**（239 + 4）。

## 实测

部署后用 ok-ww 自带解释器直接启动 `working/main.py`：

```
INFO MainThread ScheduleTaskTab:Loaded 11 tasks
```

无 `ok:__init__ error`，任务列表正常加载（日志里唯一那条 `PyAppify does not support checking
for updates for pyappify_version: None` 是绕过启动器直接跑 python 导致的环境变量缺失，不是代码问题）。

## 顺便更正 v1.8.3 的说法

v1.8.3 把版本 tag 钉到定制提交，说「启动器不会再把它刷回官方」。这次事故补上了另一半真相：

- `repo/.git/logs/HEAD` 里 23:56:31 那条 `checkout: moving from 9d33201 to 9d33201` ——
  **目标就是我们自己的定制提交**，但事后 `HEAD` 仍是官方 `567f025`、`working/config.py` 回到 13380 字节；
- 说明启动器遇到「启动失败 / 判定安装损坏」时，会**从官方文件整份重装**，这一步不经过 git，
  tag 钉得再准也拦不住。

所以准确表述是：

| 场景 | 结果 |
| --- | --- |
| 正常启动、文件与 git 一致 | 不会覆盖（v1.8.3 的 tag + 提交在这一路径上有效） |
| 启动崩溃 / 启动器判定损坏 → 自动修复 | **会**整份覆盖成官方，需要重跑 `restore.py` |

结论：让代码**能正常启动**才是第一道防线；这次的崩溃就是被这条链放大的。

## 升级

```
python restore.py
```

然后正常启动 ok-ww。若哪天又发现定制消失，直接再跑一次 `restore.py` 即可，账号与任务配置不动。

# v1.8.4 · Fix crash on startup (stale `MuMu/安卓 Config` reference)

## Symptom

At 23:56 ok-ww failed three times during startup and exited:

```
RuntimeError: Can not find global config MuMu/安卓 Config
  at src\task\BaseWWTask.py, line 123, in __init__
```

Task initialisation goes `AutoCombatTask → BaseCombatTask → CombatCheck → BaseWWTask`, and
`BaseWWTask.__init__` reads the Android formation config by name. The name no longer existed, so the
whole init chain aborted and the app quit.

## Root cause

v1.8.1 renamed the global config from `MuMu/安卓 Config` to **`MuMu 安卓 Config`** (a config name must
not contain `/`, otherwise the framework stores it under `configs/<name>.json` and the slash becomes a
subdirectory) — but only the **registration** in `config.py` was updated. The **reader** at
`src/task/BaseWWTask.py:123` still used the old name, so it could never match. Every task
initialisation hits that line, so this was not a "MuMu feature is broken" bug — the program could not
start at all. Nobody launched ok-ww between the v1.8.1 deploy and 23:56, which is why it only surfaced
then.

## Fix

1. `BaseWWTask.py:123` now uses `get_global_config('MuMu 安卓 Config')`;
2. comments referring to that config unified in `BaseWWTask.py` / `BaseCombatTask.py`;
3. new `tests/TestGlobalConfigRefs.py` (**4 tests**, pure AST, no import of `config.py`, so no
   cv2/PySide6 dependency): registered names parse correctly, no `/` in registered names, every
   `get_global_config('<name>')` literal in `src/` must be registered, and every `*_CONFIG_NAME`
   constant must be registered too.

**243 tests pass.**

## Verified

Starting `working/main.py` with ok-ww's own interpreter logs `ScheduleTaskTab:Loaded 11 tasks` and no
`ok:__init__ error`.

## Correction to v1.8.3

v1.8.3 claimed pinning the version tag meant "the launcher can no longer revert the customizations".
This incident shows the other half: the reflog entry at 23:56:31 (`checkout: moving from 9d33201 to
9d33201`) targets **our own custom commit**, yet HEAD ended up at official `567f025`. When the launcher
decides the installation is broken, it reinstalls official files wholesale — that path bypasses git
entirely. Pinning the tag only helps on the normal startup path; a crash-triggered repair still wipes
everything and needs another `restore.py` run.

## Upgrade

Run `python restore.py`, then start ok-ww normally.
