# v1.5.4 · 修复 MuMu 打着打着就停 / Fix MuMu combat stalling mid-fight

## 中文

### 问题现象

v1.5.3 修好了「进不了战斗」后，用户仍反馈「还是不战斗」。抓运行时日志发现其实**战斗已经进入、
角色也在出招**（`进入战斗` + `Rover: routine=basic`），但打着打着就停了。日志里反复刷：

```
switch_next_char Rover(MainDps) -> Rover(SubDps)
not in team while switching chars_Rover_to_Rover 0.00 ... 3.89
ERROR switch too long failed chars_Rover_to_Rover, 5.04
combat_once out of combat break
```

### 根因：切人时依赖了会短暂失效的画面判定

v1.5.2 已经让安卓端用脚本维护的逻辑下标 `_android_current_index` 代替画面识别当前角色，
但 `switch_next_char()` 的循环里还有**两处**直接读 `in_team()` 的返回值：

```python
_, current_index, _ = self.in_team()          # 循环开头
...
in_team, current_index, size = self.in_team() # 发键后
```

安卓端 `in_team()` 最终走 `in_team_android()` → `android_world.in_android_world()`，靠右上角
圆形头像、雷达黄色箭头等 HUD 元素判定。**切人 / intro 入场动画期间这些 HUD 元素会短暂消失或变化**，
判定返回 `(False, -1, 1)`：

- `not in_team` → 进入「等待 HUD 恢复」分支，等满 5 秒后 `raise_not_in_combat('switch too long failed')`
- `current_index = -1` → 即使 HUD 恢复，`-1 != switch_to.index` 也会等 10 秒抛 `failed switch chars`

两种路径都会**在每次切人时中断战斗**，表现出来就是「打着打着不打了」。这是 v1.5.2 修复的遗漏点：
逻辑下标虽然维护了，但切人循环没有完全改用它。

### 修复

核心思路：安卓端切人全程只信任脚本自己维护的逻辑下标，不读会因动画失效的画面判定。

**`BaseCombatTask.switch_next_char()`：**

1. 循环开头：安卓端用 `getattr(self, '_android_current_index', 0)` 代替 `in_team()` 的 index。
2. 发键后第二次取值：同样用逻辑下标覆盖 `in_team()` 返回的 -1。
3. `not in_team` 的「等待 5 秒 + raise」分支加 `and not self.is_adb()` 限定，安卓端不再走它；
   改为一条 debug 日志说明「动画期间 HUD 消失，用逻辑下标」。

PC / 云游戏分支完全不动，仍走原来的 `in_team()` 判定。

### 验证

- 用运行日志逐帧核对：修复前每次切人固定卡 5.04 秒抛异常；修复后切人循环用逻辑下标，
  `current_index` 发键后即为 `switch_to.index`，直接进入完成分支，不再等待/抛异常。
- 新增 `TestAndroidTargetKey.TestAndroidSwitchNoStuck`（3 项），断言循环两处都用逻辑下标、
  `not in_team` 等待分支仅限非 adb。连同 v1.5.3 的 10 项共 13 项全绿。
- 回归 `TestAndroidCombatFix`（13 项）、`TestCloudCombatFixes`（4 项）全绿。
- 修改文件在 `restore.py` 32 文件清单内，三处哈希一致、编译通过。

## English

### Symptom

After v1.5.3 fixed "can't enter combat", the user still reported "still not fighting". Runtime logs showed
combat **was** entered and the character **was** attacking (`进入战斗` + `Rover: routine=basic`),
but it stalled mid-fight:

```
switch_next_char Rover(MainDps) -> Rover(SubDps)
not in team while switching chars_Rover_to_Rover 0.00 ... 3.89
ERROR switch too long failed chars_Rover_to_Rover, 5.04
combat_once out of combat break
```

### Root cause: character switching relied on a HUD check that flickers during animations

v1.5.2 already made Android use a script-maintained logical index (`_android_current_index`) instead of
reading the current character from the screen. But `switch_next_char()` still read `in_team()` directly
in **two** places:

```python
_, current_index, _ = self.in_team()          # loop start
...
in_team, current_index, size = self.in_team() # after sending the key
```

On Android, `in_team()` goes through `in_team_android()` → `android_world.in_android_world()`, which
detects circular portraits, the radar arrow and other HUD elements. **During character-switch / intro
animations these HUD elements briefly disappear**, so it returns `(False, -1, 1)`:

- `not in_team` → enters the "wait for HUD" branch, then `raise_not_in_combat('switch too long failed')` after 5s
- `current_index = -1` → even after HUD returns, `-1 != switch_to.index` waits 10s and raises `failed switch chars`

Both paths **interrupt combat on every switch**, which looks like "fighting then suddenly stops".
This was a leftover from the v1.5.2 fix: the logical index was maintained but the switch loop wasn't fully
converted to use it.

### Fix

On Android, character switching now trusts only the script-maintained logical index, never the
animation-sensitive screen check.

**`BaseCombatTask.switch_next_char()`:**

1. Loop start: use `getattr(self, '_android_current_index', 0)` instead of `in_team()`'s index.
2. After sending the key: likewise override `in_team()`'s -1 with the logical index.
3. The `not in_team` "wait 5s + raise" branch is now guarded by `and not self.is_adb()`; Android logs
   a debug line ("HUD hidden during animation, using logical index") and continues instead.

PC / cloud-gaming branches are untouched and keep the original `in_team()` behavior.

### Verification

- Correlated runtime logs: before the fix every switch stalled exactly 5.04s then raised; after the fix
  the loop uses the logical index, which equals `switch_to.index` right after the key is sent, so it takes
  the success branch immediately with no wait/exception.
- Added `TestAndroidTargetKey.TestAndroidSwitchNoStuck` (3 tests) asserting both index reads use the
  logical index and the `not in_team` wait branch is non-adb only. Together with v1.5.3's 10 tests:
  13 passing.
- Regressions `TestAndroidCombatFix` (13 tests) and `TestCloudCombatFixes` (4 tests) all passing.
- Modified file is in the `restore.py` 32-file manifest; hashes match across repo / working / install
  directories and compilation succeeds.
