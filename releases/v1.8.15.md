# v1.8.15 · MuMu 方块拖拽改用 IPC 触控（修复 x/y 落点大幅偏移）/ Blocks drag via MuMu IPC touch

本版改了运行时代码，**必须重跑 `python restore.py` 并重启 ok-ww** 才生效。

## 现象

v1.8.14 实机反馈：MuMu 下方块拖拽时 **x、y 落点偏差超级远**，方块根本到不了预期格：
用户截图里棋盘与手的位置完全对不上，`Placement preview did not match` 反复出现。

## 根因（确认）

v1.8.14 把拖拽从 `sendevent` 改成了 `input motionevent`，但踩了另一套坐标系的坑：

- `input motionevent`（以及所有 `input` 命令）传的是 Android 的 **wm size 逻辑显示坐标**。
- MuMu 横屏游戏时，`wm size` 报的是**竖屏**尺寸（典型 `900x1600`），而截图/游戏画面是**横屏** framebuffer（典型 `1600x900`）。
- v1.8.14 的 `AdbMotionEventDevice.game_to_touch()` 把坐标当成横屏 1920x1080 原样交给 `input motionevent`，
  等于拿横屏坐标去喂竖屏坐标系 —— x、y 双向错位，而且偏差极大。

> v1.8.14 说明里「`input tap 712 343` 能点中弹窗按钮，证明 input 坐标就是画面坐标」的推断在 MuMu 上不成立：
> MuMu 的 input 走 wm size（竖屏），与截图 framebuffer（横屏）不是一套。

## 修复：改用 MuMu IPC 触控（截图 framebuffer 坐标）

新增 `NemuIpcTouchDevice`（`src/task/multi_touch.py`），用 MuMu IPC SDK 的
`nemu_input_event_touch_down/up` 注入触点：

- **坐标与截图 framebuffer 完全一致**（就是横屏画面像素），正是 `interaction` 传进来的坐标空间，
  无需任何竖屏/横屏换算。`game_to_touch()` 只做与 `AdbMotionEventDevice` 相同的 2048x1152 → 画面等比还原，
  最终坐标就是 `_place()` 里 `point()` 算出的截图像素坐标。
- 依据是官方框架的 `ADBInteraction.swipe_nemu`：它把任务屏幕坐标**直接**传给 `nemu_impl.down(*point)`，
  其 `convert_xy`（竖屏→横屏换算）是**注释掉**的 —— 证明 IPC 触控 API 期望的就是截图坐标。
- `RahaiBlocksTask._make_interaction()` 在 MuMu（IPC 抓屏可用）下优先用该设备；
  非 IPC 抓屏/低版本回退到 v1.8.14 的 `AdbMotionEventDevice`，保留兼容。
- 旋转仍走 v1.8.13 的键位映射键（真实键盘 F1 → 游戏内旋转按钮），与触屏拖拽互不干扰。
- IPC 是单指 API（连续 down 视为 swipe、up 抬全部触点）；拖拽只需单指，够用。

## 你需要做的

1. 重跑 `python restore.py`，重启 ok-ww。
2. 抓屏方式保持 **IPC**（`devices.json` 的 `capture` = `ipc`）；若被改成 adb/windows，会回退到旧方案、偏移仍在。
3. 保持 v1.8.13 的键位映射（MuMu 里 F1 → 旋转按钮），`Rotate Key (MuMu Keymap)` 仍为 `f1`。
4. 实机跑一局方块，确认拖拽落点与预览一致（本版不做实机验证，由用户自行确认）。

## 验证

- 新增 7 项 `NemuIpcTouchDevice` 单测（截图坐标还原、down/move/up 坐标、tap、close 释放、无 IPC 连接报错），
  更新无尽模式测试覆盖「IPC 优先 / 非 IPC 回退」两条分支，全量 **340 项通过**。
- 实机落点验证由用户完成。
