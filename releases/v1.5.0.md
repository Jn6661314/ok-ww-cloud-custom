## 中文

### 梦魇聚落（残象聚落）点不开

- **根因是"传送按钮认不出来"，不是点击坐标错**。聚落条目点开后是「详情页 + 右下角黑底白字的**快速旅行**按钮」，而脚本只会找 `fast_travel_custom` / `gray_teleport` / `remove_custom` 三个 PC 模板。实测 1920×1080 云游戏与安卓截图上，这三个模板最高匹配度只有 **0.02 ~ 0.28**，远低于 0.7 阈值，`wait_feature` 直接抛异常 → 日志 `NightmareNestTask Failed`。
- **修复**（`src/task/BaseWWTask.py` 新增 `find_travel_button()` / `find_travel_button_by_ocr()` / `find_confirm_button()` / `find_confirm_button_by_ocr()`）：
  - 模板找不到时用 **OCR 认「快速旅行」**，实测 `onnxocr` 在右下角 `(0.7,0.89)-(1,1)` 区域置信度 **0.99998**（坐标 1535,985 / 126×40）。
  - 点完传送若弹确认框（`确认` / `確定` / `确定`）一并点掉。
  - 「按钮是否还在」的判定只对同名模板成立，OCR 按钮改为直接等回到大世界。
- **新增覆盖层文件** `src/task/NightmareNestTask.py`（基于上游 v3.8.13 的 `NightmareNestTask.py`），`combat_nest` 改用新的 `wait_travel_or_team()`，`_travel_to_nest_or_skip` 重写。
- 已加入 `restore.py` 的 `RELATIVE_FILES`（定制文件 31 → 32）。

### 登录后黑屏被误判为抓屏失败

- 模拟器点完登录后正常黑屏十几秒（游戏载入资源），MuMu IPC 此时返回纯黑帧；旧逻辑重试 3 次（约 1.5 秒）就抛 `CaptureException`，**每日任务被直接断掉**（21:09 / 21:13 的 `error_DailyTask_CaptureException` 截图佐证）。
- **修复**（`ok/device/capture_methods/nemu_ipc.py`）：新增 `BLACK_FRAME_GRACE_PERIOD = 30` 秒**冗余等待窗口**。窗口内全黑一律当作"登录/加载中"继续等（第一帧黑时重建一次 IPC 连接，同一段黑屏不再反复重连），超过 30 秒仍是全黑才抛带秒数的明确异常。

### 安卓设备启动时用 adb 拉起鸣潮

- 模拟器/真机开机后游戏不会自动运行；原先只有 `start_controller.check_device_error()` 里调过一次 `adb_ensure_in_front()`，而且它在**成功抓到一帧之后**才执行，模拟器桌面分辨率不匹配时会一直重试、游戏始终没被拉起。
- **修复**（`ok/device/DeviceManager.py`）：安卓设备启动分支（`do_start` 的 adb 分支）主动调 `adb_start_game()` —— **等 adb 就绪 → 确认游戏不在前台 → `monkey -p <包名> -c android.intent.category.LAUNCHER 1` 拉起**。
  - 已在前台则不做任何事；两次拉起之间 20 秒冷却，避免"等待设备就绪"循环反复拉起。
  - adb 还没连上时立刻返回不空等，交给下一轮重试；设备已连接但命令失败时最多等 60 秒。

### 安卓索拉指南开书判定改为模板法

- `android_book.is_book_opened` 改用模板法（笔画 IoU 配对 + 数量/跨度规则），修复大世界画面假匹配：要求 ≥3 个命中且竖向跨度 ≥200（书界面 4 个、跨度 536；大世界假匹配跨度仅 15）。

## English

### Nightmare Nest (Remnant Settlement) could not be opened

- **The root cause is "the teleport button cannot be recognized", not wrong click coordinates.** After clicking a settlement entry you land on a details page with a black button with white text reading **快速旅行** (Quick Travel) in the bottom-right corner, but the script only looks for the three PC templates `fast_travel_custom` / `gray_teleport` / `remove_custom`. Measured on 1920×1080 cloud and Android screenshots, the best match of those three templates is only **0.02 ~ 0.28**, far below the 0.7 threshold, so `wait_feature` throws immediately → the log shows `NightmareNestTask Failed`.
- **Fix** (`src/task/BaseWWTask.py` gained `find_travel_button()` / `find_travel_button_by_ocr()` / `find_confirm_button()` / `find_confirm_button_by_ocr()`):
  - When the templates do not match, **OCR reads 「快速旅行」** — measured `onnxocr` confidence **0.99998** in the bottom-right region `(0.7,0.89)-(1,1)` (at coordinates 1535,985 / 126×40).
  - If a confirmation dialog pops up after the teleport (`确认` / `確定` / `确定`), it is dismissed as well.
  - The "is the button still there" check only makes sense for a template of the same name; for an OCR-detected button the task now simply waits until it is back in the open world.
- **New overlay file** `src/task/NightmareNestTask.py` (based on the upstream v3.8.13 `NightmareNestTask.py`): `combat_nest` now uses the new `wait_travel_or_team()`, and `_travel_to_nest_or_skip` was rewritten.
- Added to `RELATIVE_FILES` in `restore.py` (31 → 32 custom files).

### The black screen after login was misjudged as a capture failure

- After clicking login in the emulator the screen legitimately stays black for a dozen seconds or so (the game is loading resources), and the MuMu IPC returns pure black frames during that time. The old logic retried 3 times (about 1.5 seconds) and then threw `CaptureException`, which **cut the daily task short** (evidenced by the 21:09 / 21:13 `error_DailyTask_CaptureException` screenshots).
- **Fix** (`ok/device/capture_methods/nemu_ipc.py`): a new `BLACK_FRAME_GRACE_PERIOD = 30` second **grace window**. Inside the window an all-black frame is treated as "logging in / loading" and the capture keeps waiting (the IPC connection is rebuilt once on the first black frame, and the same black stretch no longer reconnects repeatedly); only after 30 seconds of continuous black is a clear error with the elapsed time raised.

### Launching Wuthering Waves with adb when an Android device starts

- After an emulator or a real device boots, the game does not start by itself. Previously `adb_ensure_in_front()` was called only once from `start_controller.check_device_error()`, and that happens **after a frame has been captured successfully** — so when the emulator desktop resolution does not match, it kept retrying and the game was never launched.
- **Fix** (`ok/device/DeviceManager.py`): the Android device startup branch (the adb branch of `do_start`) now actively calls `adb_start_game()` — **wait until adb is ready → confirm the game is not in the foreground → launch it with `monkey -p <package> -c android.intent.category.LAUNCHER 1`**.
  - If the game is already in the foreground nothing happens; there is a 20 second cooldown between launches so the "wait for the device to be ready" loop cannot launch it repeatedly.
  - When adb is not connected yet the call returns immediately instead of blocking, leaving the retry to the next round; when the device is connected but commands fail it waits at most 60 seconds.

### Android guidebook "is it open?" detection now uses templates

- `android_book.is_book_opened` was rewritten to use templates (stroke-IoU pairing plus count/spread rules), fixing false matches on open-world frames: it now requires ≥3 hits with a vertical spread ≥200 (the guidebook screen gives 4 hits with a spread of 536, while the open-world false matches have a spread of only 15).
- `open_touch_book` now checks whether the book is already open before tapping — this fixes the previous behaviour of tapping once to close it and again to open it, flipping the book state back and forth.

- Updated `probe/test_black_frame.py` (19 assertions, including no exception inside the grace window, exception only after the window is exhausted, and the window duration cap) — all green.
