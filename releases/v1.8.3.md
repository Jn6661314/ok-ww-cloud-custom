# v1.8.3 · 堵死「启动一次就丢定制」的第二次事故

## 现象

23:30 又不小心点开了官方启动器，几秒后界面上的 MuMu/远控/多账号定制全部消失。
对比文件时间戳：`working` 和 `repo` 的 `config.py` 同时变回官方 **13380 字节**（定制版是 17430），
一次批量覆盖 22 个**已被 git 跟踪**的文件。

## 为什么 v1.8.2 的「提交进 git」没挡住

v1.8.2 的结论是：定制只要以「未提交改动」存在，启动器的完整性校验就会把它还原，所以要把定制
提交成 git 里的一个提交。这个结论**只对了一半**。

真相在 `repo/.git/logs/HEAD`（reflog）里：

```
9d33201 HEAD@{0}: commit: local custom baseline ...          ← 本次修复后
567f025 HEAD@{1}: checkout: moving from bb9c990 to bb9c990   ← 启动器
bb9c990 HEAD@{2}: commit: local custom baseline ...          ← v1.8.2 的定制提交
567f025 HEAD@{3}: checkout: moving from e2cc611 to e2cc611   ← 启动器
e2cc611 HEAD@{4}: reset: moving to e2cc611                   ← 启动器
```

启动器根本不是在「校验工作区有没有改动」，它是拿 `app.json` 的 `current_version`（`v3.8.15`）
去仓库里找**同名 tag `v3.8.15`**，然后 `git checkout -f <tag>`。

- tag `v3.8.15` 指向官方提交 `567f025` → `-f` 强制把工作区刷成官方树；
- 我们的定制提交 `bb9c990` 只是"当时的 HEAD"，被 `checkout -f` 一秒钟甩掉；
- 所以「提交进 git」在启动器眼里毫无意义 —— 它只认版本 tag。

一句话：**定制提交能防住「`git checkout -- .`」式的还原，防不住「`git checkout -f <官方tag>`」。**

## 修复

`restore.py` 新增 `pin_version_tag_to_head()`，在定制提交完成后把**版本 tag 本身**指向该提交：

1. 读 `config.py` 的 `version`（`v3.8.15`）= 启动器要找的 tag 名；
2. 若 tag 已有指向且不是 HEAD → 先把原指向备份成 `official-v3.8.15`（只备份一次，不会被二次覆盖）；
3. `git tag -f -a v3.8.15 -m "ok-ww v3.8.15 (local custom baseline)" HEAD`；
4. 若 tag 已指向 HEAD → 打印「无需改动」，不产生新对象。

这样启动器再执行 `git checkout -f v3.8.15`，切出来的就是我们自己的树，校验只在校验定制版。

已在本机执行并验证：

| 检查 | 结果 |
| --- | --- |
| `git rev-parse v3.8.15^{commit}` | `9d33201`（定制提交） |
| `git checkout -f v3.8.15` 后 `repo/config.py` | 17430 字节（定制） |
| 同一条 checkout 后 `working` 已跟踪文件 | 与 git 一致（仅 `Aemeath.py` 行尾 CRLF 归一差异） |
| 重复跑 `restore.py` | 「版本 tag 已指向定制提交，无需改动」 |
| 官方指针备份 | `official-v3.8.15` → `567f025` |

想回官方基线时：`git checkout official-v3.8.15`。

## 边界（诚实说明）

移动 tag 只能挡住「按当前版本号 checkout」。如果哪天官方发了 v3.8.16、`app.json` 被启动器刷新，
再点「安装更新」，官方代码仍会覆盖 `working`/`repo` —— 这是启动器的固有行为，除非不用启动器。
真发生了就重跑 `python restore.py`，它会重新提交并重新钉 tag。

## 测试

`tests/TestRestoreGitSync.py` 从 8 项扩到 **13 项**，新增 5 项：

- 官方 tag 存在时被移到定制提交，且原指向备份成 `official-<版本>`；
- tag 不存在时自动创建并指向 HEAD；
- 已指向 HEAD 时重复运行不改动、不重复备份（幂等）；
- 非 git 仓库安全跳过；
- 读不到 `version` 时安全跳过。

全量 **239 项通过**。

## 升级

```
python restore.py
```

然后正常启动 ok-ww。这次的定制是从「版本 tag 里的提交」切出来的，启动器不会再把它刷成官方版。

# v1.8.3 · Stop the "one launcher start wipes the customizations" incident for good

## Symptom

At 23:30 the official launcher was opened again by accident; seconds later the MuMu / remote-window /
multi-account customizations were gone from the UI. Timestamps show `config.py` in **both** `working`
and `repo` reverted to the official **13380 bytes** (custom is 17430) — 22 **git-tracked** files
overwritten in one batch.

## Why v1.8.2's "commit the customization" did not help

v1.8.2 assumed the launcher's integrity check restores tracked files from git, so committing the
customizations should be enough. That was **half** right. `repo/.git/logs/HEAD` tells the real story:

```
9d33201 HEAD@{0}: commit: local custom baseline ...          ← after this fix
567f025 HEAD@{1}: checkout: moving from bb9c990 to bb9c990   ← launcher
bb9c990 HEAD@{2}: commit: local custom baseline ...          ← v1.8.2 custom commit
567f025 HEAD@{3}: checkout: moving from e2cc611 to e2cc611   ← launcher
e2cc611 HEAD@{4}: reset: moving to e2cc611                   ← launcher
```

The launcher does not diff the work tree. It takes `current_version` from `app.json` (`v3.8.15`),
looks up the **tag of the same name**, and runs `git checkout -f <tag>`. That tag pointed at the
official commit, so `-f` force-overwrote the work tree; our custom commit was merely "current HEAD"
and got dropped instantly. **A custom commit survives `git checkout -- .` but not
`git checkout -f <official tag>`.**

## Fix

New `pin_version_tag_to_head()` in `restore.py`, run right after the custom commit:

1. read `version` from `config.py` (`v3.8.15`) — that is the tag name the launcher looks for;
2. if the tag points somewhere else, back the original target up as `official-v3.8.15` (once only);
3. `git tag -f -a v3.8.15 ... HEAD`;
4. if it already points at HEAD, print "no change needed" and stay idempotent.

Now the launcher's `git checkout -f v3.8.15` checks out our own tree, so any check only validates the
custom version.

Verified on this machine: tag → `9d33201`; after `git checkout -f v3.8.15`, `repo/config.py` is 17430
bytes; `working` tracked files match git (only an `Aemeath.py` CRLF-normalization difference); a second
`restore.py` run reports "already pointing at the custom commit"; official pointer preserved as
`official-v3.8.15` → `567f025`. To return to upstream: `git checkout official-v3.8.15`.

## Honest limitation

Pinning the tag only blocks "checkout the current version". If upstream ships v3.8.16 and someone
clicks Install in the update card, official code still overwrites `working`/`repo` — that is the
launcher's inherent behaviour. If it happens, run `python restore.py` again; it re-commits and
re-pins the tag.

## Tests

`tests/TestRestoreGitSync.py` grows from 8 to **13 tests**, adding 5: official tag moved with backup,
tag created when missing, idempotent re-run, non-git directory, missing version.
**239 tests pass** overall.

## Upgrade

Run `python restore.py`, then start ok-ww normally.
