# v1.8.20 · 内置投屏引擎：把 NectarLink 桌面端装进 ok-ww，不再装外部软件、不再有分辨率问题 / Built-in mirroring engine: NectarLink inside ok-ww

本版改了运行时代码并新增一个二进制文件，**必须重跑 `python restore.py` 并重启 ok-ww** 才生效。

## 背景

v1.8.19 把 NectarLink 的**手机投屏窗口**接进了 ok-ww，但仍有三个绕不开的问题：

1. **还得装桌面端**：NectarLink 桌面端是个 Qt 程序（几百 MB），只为了投屏装它不划算；
2. **分辨率契约打架**：投屏窗口客户区里混着工具条与黑边，框架按 16:9 校验会报
   `resolution error 2560x1494` 并弹红色错误框；
3. **窗口尺寸不由自己定**：画面比例跟着桌面端窗口走，拖一下窗口就变一次，
   模板资源要跟着反复重载。

根因是「投屏」这件事被放在了 ok-ww 之外。既然 NectarLink 是开源的（`github.com/thtbee/nectarlink`），
那就把它真正需要的那部分——**协议内核**——直接编进 ok-ww。

## 本版做了什么

### 1. 新增内置投屏内核 `nectarlink-sidecar`（Rust，MPL-2.0）

在 nectarlink 仓库新增 `core/nectarlink-sidecar` crate：无界面，只干三件事——

* 用自己的设备身份跟手机配对、请求投屏（QUIC/iroh 协议栈直接复用 `nectarlink-core`，不重写）；
* 用 **Windows 自带的 Media Foundation H.264 解码器**把手机的 H.264 画面解成 NV12
  （自己实现，没抄桌面端那段 GPL-3.0 的 D3D11 代码，也不需要 FFmpeg 之类的额外依赖）；
* 通过 `127.0.0.1` 上的一个 socket 把画面推给 ok-ww，并把 ok-ww 的点击/按键原样回传给手机。

socket 协议很简单：`1 字节类型 + 4 字节长度(小端) + 负载`，
类型 1=状态(JSON)、2=画面(NV12)、3=触控、4=按键。

状态行走的是**同一条 socket**，所以只拿到 socket 的宿主也能知道
「画面格式变了 / 解码出错 / 手机停止投屏 / 实际分辨率是多少」，不必再去读 stdout。

内核把端口写在 `%LOCALAPPDATA%\ok-ww\nectarlink\link.json` 里，
所以**跨次运行可以复用同一个内核**——每次重新投屏都要在手机上点「允许」，能少重启就少重启。

成品 `bin/nectarlink-sidecar.exe`（约 24 MB）随本仓库一起分发。
源码在**本仓库的 `nectarlink-sidecar-src/` 目录**（Rust，MPL-2.0），
也可以在上游 nectarlink 仓库的 `core/nectarlink-sidecar` 找到
（`cargo build -p nectarlink-sidecar --release`）。
本仓库里那份是**独立构建版**：依赖写死版本、`nectarlink-core` 走 git 依赖，
不依赖上游的 workspace 布局。

### 2. ok-ww 侧：画面从 socket 来，点击直接变成手机触点

新增 `ok/device/capture_methods/phone_mirror_socket.py`：
后台线程收帧（只保留最新一帧，慢了就丢旧的）、裁掉手机画面两侧的黑边、
等比归一化到模板原生高度 1080（帧尺寸恒定 → 模板按 1:1 使用，最准）。

新增 `ok/device/interaction_methods/phone_mirror.py`：
点击 = 触点按下+抬起，滑动 = 按下+多段移动+抬起，按键 = 手机上的 back/home/recents 等。
**不再走真实鼠标**（Pynput），所以投屏窗口不需要在前台，鼠标也不会乱飘。

坐标换算沿用协议本来的约定（`docs/protocol/mirror.md` §4）：
发的是**屏幕比例 0..1**，与手机当前的画面尺寸、横竖屏、缩放无关。

内核在 socket 上报「手机停止投屏」时，ok-ww 会**丢掉缓存的那一帧**：
否则框架会一直对着一张旧截图点，看起来像「点了没反应」。

### 3. 新增全局配置「手机投屏(内置引擎)」

| 项 | 说明 |
| --- | --- |
| `Enable` | 开启后设备下拉里出现「手机投屏(内置引擎)」，改完需重启 ok-ww |
| `手机` | 要投屏的手机（id 前缀或名字），留空表示只有一台时自动选 |
| `画面宽度` | 向手机请求的最长边（默认 1920，即 1080p） |
| `帧率` | 向手机请求的帧率（默认 30） |
| `码率` | 向手机请求的码率（默认 8 Mbps） |
| `配对手机` | 按钮：打开配对窗口，手机扫码即可（只需一次） |
| `启动投屏内核` | 按钮：立刻把内核跑起来 |

配对窗口用 **OpenCV 自带的二维码编码器**画配对链接（ok-ww 本来就带 OpenCV，不需要额外库），
手机用 NectarLink 客户端扫一下；随后弹出 6 位配对码，核对一致后点「我看到的码一致」。

### 4. 分辨率契约彻底放宽

投屏模式下 `supported_resolution` 的 `ratio / min_size / resize_to` 全部置空
（v1.8.19 已做了一半），框架的 `check_frame_and_resolution` 遇到空值直接判定通过，
**不会再报 `resolution error`、不会再弹错误框、也不会去 resize 任何窗口**。

## 你需要做的

1. **手机端**：装好 NectarLink 的 Android 客户端（配置里有「下载手机端(网盘)」按钮）。
2. **配对**：ok-ww 配置 →「手机投屏(内置引擎)」→ 点「配对手机(扫码)」→ 手机扫码 →
   核对手机上的 6 位码一致 → 点「我看到的码一致」。
3. **开启**：同一个配置里把 `Enable` 打开，保存后**重启 ok-ww**。
4. **选设备**：设备下拉里选「手机投屏(内置引擎)」。
5. **手机端授权**：每次重新投屏，手机上都会弹系统的「屏幕录制」授权框，点允许。

## 已知限制

- **每次重新投屏都要在手机上点一次「允许」**：这是 Android `MediaProjection` 的规定
  （NectarLink 桌面端也一样），所以内核尽量保持常驻，别反复重启 ok-ww。
- **本版不做实机验证**（按你的要求）：协议内核用 nectarlink 自带的测试码流验证过能解出画面，
  ok-ww 侧用假内核做了端到端测试，但「手机扫码配对 → 授权 → 出画面 → 点击落到手机」这条链
  没有在真机上跑过，由你确认。
- 内核目前只解 **H.264**（不声明 `mirror.decode.hevc` 能力，手机就会发 H.264）。
- 投屏有编码与网络延迟，识图阈值可能要比本地 PC 放宽一点。
- 内核的解码是 Windows 的软件解码器，1080p30 没问题，再高的分辨率/帧率要观察 CPU 占用。
