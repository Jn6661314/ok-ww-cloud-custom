# v1.5.5 · 修复 MuMu 掉线弹窗卡住不动 / Fix MuMu freeze on disconnect dialog

## 中文

### 问题现象

连续多轮战斗修复后（v1.5.2 修当前角色、v1.5.3 修锁定检测、v1.5.4 修切人卡死），
用户仍反馈「还是不会自动打，动都不动」。这次抓失败瞬间的截图，真相和之前完全不同——
**不是战斗逻辑的问题，是游戏掉线了**：

```
截图 10:37:24: 中央弹出【连接已断开】对话框
"已与服务器断开连接，请尝试重新登录，如有疑问请联系客服" + 确认按钮
整个画面被遮罩变暗
```

运行日志时间线也印证：

```
10:28:00 AndroidDailyTask:Game disconnected, closing the notice and logging in again   ← 这次成功重登了
...
10:36:04 CombatCheck:target lost try retarget 10
10:36:45 ERROR CombatCheck:target_enemy failed, try recheck break out of combat
10:36:47 BaseCombatTask:combat_once out of combat break
10:37:24 AndroidDailyTask:WaitFailedException（截图即掉线弹窗）
```

### 根因：掉线检测只在 is_main()，触发任务/战斗循环走不到

代码里其实**早就有**安卓掉线弹窗处理 `handle_android_disconnect()`（点确认 + 复位登录态，
由 AutoLoginTask 自动重登），10:28 那次日志 `Game disconnected` 就是它成功触发的证据。

但它**只在 `is_main()` 里被调用**——也就是只有 DailyTask / AndroidDailyTask 这类一次性任务
走到 `ensure_main()` 时才会检查。而 AutoCombatTask 是**触发任务**，它的战斗循环走
`in_combat()` → `do_check_in_combat()`，完全不经过 `is_main()`。

于是当掉线弹窗出现时：

1. 弹窗遮暗画面 → `check_health_bar()` 检测不到血条（离线用正常战斗截图测是 True，运行时是暗屏所以 False）
2. `has_target()` → False → 一直 `target lost try retarget`
3. `target_enemy()` 超时 → `target_enemy failed` → `break out of combat`
4. `logged_in` 一直是 True → AutoLoginTask 每 5 秒看到 True 就 `pass`，**永远不重登**

结果就是脚本卡在掉线弹窗上，既不战斗也不重新登录——用户看到的「动都不动」。
这也解释了为什么有时能恢复（一次性任务走到 `is_main()` 触发了检测）、有时卡死（触发任务走不到）。

### 修复（只动安卓端，PC/云游戏行为不变）

1. **战斗判定入口接入掉线检测**：`CombatCheck.do_check_in_combat()` 开头加
   `if self.is_adb() and self.handle_android_disconnect(): return self.reset_to_false(...)`。
   这样触发任务和战斗循环也能检测并处理掉线弹窗。
2. **防重复点击节流**：`handle_android_disconnect()` 加 15 秒节流锁。因为战斗判定每帧都调用，
   点确认后有 2 秒 sleep、期间画面可能还是弹窗，不节流会重复点确认（弹窗消失后那一击可能落到登录页）。

重登链条（已验证有效）：点确认 → `logged_in=False`（全局 `og.my_app` 共享）→
AutoLoginTask 每 5 秒检测到 False → `wait_login()` 重新登录 → 10:28 的日志证明这条路在本机跑通过。

### 验证

- 像素级：10:37 真实掉线截图 `has_center_dialog()` 返回 `(True, 0.777)` 能识别；
  10:21 正常战斗截图不误判为弹窗（避免战斗中误点确认）
- 新增 `tests/TestAndroidDisconnect.py` 7 项全绿（含掉线 reset、非 adb 不拦截、节流、两截图）
- 回归：`TestAndroidTargetKey` 13 项、`TestAndroidCombatFix` 13 项、`TestCloudCombatFixes` 4 项全绿
- 改动在 `restore.py` 32 文件清单内，已同步 working + repo，三处哈希一致、编译通过

## English

### Symptom

After several rounds of combat fixes (v1.5.2 current character, v1.5.3 target detection,
v1.5.4 switch-character stall), the user still reported "it just won't auto-fight, nothing moves".
This time the failure-moment screenshot revealed a completely different cause —
**it wasn't a combat-logic issue, the game had disconnected**:

```
Screenshot 10:37:24: a [Connection Lost] dialog in the center
"Disconnected from server. Please try logging in again." + Confirm button
The whole screen is dimmed by the modal overlay
```

The runtime log timeline confirms it:

```
10:28:00 AndroidDailyTask:Game disconnected, closing the notice and logging in again   <- re-login succeeded this time
...
10:36:04 CombatCheck:target lost try retarget 10
10:36:45 ERROR CombatCheck:target_enemy failed, try recheck break out of combat
10:36:47 BaseCombatTask:combat_once out of combat break
10:37:24 AndroidDailyTask:WaitFailedException (screenshot = the disconnect dialog)
```

### Root cause: disconnect check only lived in is_main(), unreachable from trigger/combat loops

The code **already had** Android disconnect handling `handle_android_disconnect()` (dismiss the
dialog + reset login state, letting AutoLoginTask re-login); the 10:28 `Game disconnected` log is
proof it worked.

But it was **only called from `is_main()`** — i.e. only when one-shot tasks like DailyTask /
AndroidDailyTask reach `ensure_main()`. AutoCombatTask is a **trigger task**; its combat loop goes
`in_combat()` → `do_check_in_combat()` and never passes through `is_main()`.

So when the disconnect dialog appeared:

1. The dimmed overlay made `check_health_bar()` fail (offline tests with a normal battle screenshot pass;
   at runtime the screen was dimmed, so it returned False)
2. `has_target()` → False → endless `target lost try retarget`
3. `target_enemy()` timed out → `target_enemy failed` → `break out of combat`
4. `logged_in` stayed True → AutoLoginTask sees True every 5s and `pass`es → **never re-logs in**

Result: the script froze on the disconnect dialog, neither fighting nor re-logging in — exactly the
"nothing moves" the user saw. This also explains why it sometimes recovered (a one-shot task hit
`is_main()`) and sometimes froze (a trigger task never did).

### Fix (Android only; PC/cloud behavior unchanged)

1. **Hook disconnect detection into the combat-check entry point**: at the top of
   `CombatCheck.do_check_in_combat()` add
   `if self.is_adb() and self.handle_android_disconnect(): return self.reset_to_false(...)`.
   Trigger tasks and combat loops can now detect and handle disconnects too.
2. **De-bounce repeated clicks**: add a 15-second throttle to `handle_android_disconnect()`.
   Combat checks run every frame; dismissing the dialog has a 2s sleep during which the frame can
   still show the dialog, so without throttling it would click Confirm twice (the second click
   landing on the login page after the dialog closes).

Re-login chain (verified working): dismiss dialog → `logged_in=False` (shared globally via
`og.my_app`) → AutoLoginTask detects False every 5s → `wait_login()` re-logs in — the 10:28 log
proves this path works on this machine.
