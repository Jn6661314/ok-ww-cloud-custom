# v1.8.23 — 修好「手机投屏启动不了」（内核起来就自己退）

v1.8.22 把二维码修好了，配对能走通。但真机再试时投屏起不来：
配对之后点「启动投屏内核」，日志里没几句有用的信息，投屏窗口也不出现。

## 问题出在哪

单独跑内核复现，stderr 里终于有了实话：

```
Error: "the phone did not agree to share its screen: device is offline"
```

关键是这个 **23ms**——节点刚启动，**23 毫秒**后就去请求投屏了。

### 1. 请求投屏的时机不对（根本原因）

`mirror_start` 要求**会话已经存在**（手机和这台电脑之间已经握手成功）。
但节点刚起来的时候，后台还在拨号重连，握手根本还没完成 ——
这时候去请求投屏，拿到的是必然的 `device is offline`，内核随即自己退出。

上游 NectarLink CLI 在同一件事上**先等设备上线、再开口**：

```rust
// nectarlink-cli/src/main.rs
wait_until_online(...).await?;   // ← 我们这边少了这一步
node.mirror_start(...).await?;
```

我们把这一步漏了，所以每次都是「内核起来 → 立刻退」。

### 2. 三个内核用同一个身份在局域网里互抢（更隐蔽的那个）

排查时还发现**同时有 3 个 `nectarlink-sidecar.exe` 在跑**，用的是**同一个设备身份**
（`u3kn9obp`）、占着 3 个不同 UDP 端口、并且在 mDNS 上广播同一个 NodeId。

手机拿到的是对不上的地址 → iroh 判定「设备离线」。

也就是说：**就算加了等待，只要上一轮的内核没退干净，还是连不上**。
ok-ww 之前不管有没有残留内核，直接再起一个。

### 3. 失败原因被扔掉了

内核的 stderr 之前是 `subprocess.DEVNULL` —— 直接扔进垃圾桶。
所以界面上只能显示一句没头没尾的「投屏内核还没就绪」，
用户完全不知道是「手机没上线」还是「手机没点允许」。

## 改了什么

### 内核侧（`nectarlink-sidecar-src/src/main.rs`）

- **新增 `wait_until_online()`**：请求投屏前先等手机上线。
  判据是 `paired_devices()` 里 `LinkState::Online`（有会话 = 能投屏），
  每 300ms 查一次，默认最多等 **120 秒**（`--wait-seconds` 可调）；
  等待期间每 10 秒发一条 `waiting` 状态，**不让界面看着像卡死**；
  超时了也会说清楚是「手机没上线，NectarLink 应用是不是没在运行」。
- **投屏请求失败会自动重试**：`Offline` / `Network` / `Timeout` 这三种
  （都属于「连接问题」）会重新等上线再试，最多 5 次；
  手机刚同意时连接常常要重建一次，这种情况以前就是直接失败。
- **新增 `sidecar.json` 状态文件**：记录本进程 pid + 画面端口，
  进程退出时自动删除（只删属于自己的那份，别人接管了就不动）。
- **错误也走 stdout 的 JSON 通道**：`main()` 拆成 `run()`，
  失败时先发一条 `{"type":"error","message":...}` 再退出 ——
  stdout 是 ok-ww 唯一保证能读到的通道，不能只依赖 stderr。
- **关掉日志里的颜色转义码**（`with_ansi(false)`）：颜色码会把
  ` INFO ` 拆成两半，导致「哪些是日常信息、哪些是真错误」判断失效。

### ok-ww 侧（`src/phone_mirror_engine.py`）

- **捕获内核 stderr**，保留最后几行（过滤掉 tracing 的 INFO/DEBUG 日常日志），
  通过 `failure_reason` 把真实原因交给界面 —— 现在显示的是
  「投屏内核还没就绪: 设备离线」这类**说人话**的内容，
  而不是一句「还没就绪」。
- **启动前清掉残留内核**：先读 `sidecar.json` 里的 pid，
  再按命令行扫一遍同数据目录的 `nectarlink-sidecar.exe`，把不是自己的都结束掉。
- **`pid_alive()` 走 Windows API**，不用 `os.kill(pid, 0)` ——
  **Windows 上 `os.kill(pid, 0)` 会直接 TerminateProcess**，
  「试探进程还在不在」这个动作本身就会把进程杀掉。这个坑很隐蔽。
- **配对模式与普通模式自动切换**：跑着普通内核时点「配对手机」，
  引擎会换成一个配对内核起来（以前一直等不到二维码）；
  点「启动投屏内核」则确保是普通模式。
- 内核退出时把 stdout/stderr/stdin 管道都关掉，不一直占着句柄。

### ok-ww 侧（`ok/device/DeviceManager.py`）

等就绪的超时改成**看内核死活**：内核还活着（还在等手机上线/等手机上点「允许」）
就多等 30 秒；内核已经退了就没必要等，直接把它报的原因说出来。

### ok-ww 侧（`src/phone_mirror_pairing.py`）

配对码还没拿到之前，「我看到的码一致」/「不一致」两个按钮**不可点**
（那会儿内核不会读标准输入，白点一下只会写失败）；
状态栏优先显示内核的真实进度（「等手机上线…」「手机已上线…」）。

## 验证

- **根因复现**：干净环境单实例实跑，修复前 23ms 就 `device is offline` 退出；
  修复后等到 `online` → 拿到 `config` → `ready` 出画面，
  画面流稳定保持 60 秒无中断；
- **端到端联调**：Rust 内核 → Python 收帧，跑通（内核连上手机 → 等待手机上点「允许」）；
- **孤儿内核场景**：实测 3 个同身份内核并存会互相干扰，已加清理逻辑；
- **真实内核跑通配对**：`--pair` 起来后 stdout 只有纯 JSON，
  配对链接 178 字符正确拿到；
- Rust 侧 **8 项测试通过**（新增：等待时长可配、默认值、状态文件生命周期、
  未知参数拒绝）；
- Python 侧新增 16 项测试（残留内核清理、stderr 原因提取、ANSI 剥离、
  等待状态显示、配对按钮禁用等），全量 **455 项通过**。

## 你需要做的

**重跑 `python restore.py` 并重启 ok-ww**（这版换了内核二进制，必须重新部署）。

然后配置 →「手机投屏」：

1. 先点「配对手机(扫码)」——手机上的 NectarLink 要在运行；
2. 配对成功后点「启动投屏内核」；
3. **在手机上点「允许」**（Android MediaProjection 规定每次都要点，内核会尽量常驻）。

## 说明

按约定本版**不做实机验证**。本版验证到的是「内核会等手机上线而不是秒退」
「残留内核会被清掉」「失败原因能显示出来」这三层；
「手机点允许 → 出画面 → 点击落到手机」这条链仍由使用者确认。

另外提醒：**如果之前多次点过「启动投屏内核」，可能已经有旧内核残留在后台**，
本版启动时会自动清理；如果仍有干扰，重启电脑一次即可彻底干净。
