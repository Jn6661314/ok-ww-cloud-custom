# v1.8.11 · 修复鸣潮已启动但 MuMu 报"未连接" / Fix MuMu "not connected" while game is running

本版改了运行时代码，**必须重跑 `python restore.py` 并重启 ok-ww** 才生效。

## 现象

MuMu 里鸣潮明明已经启动、adb 也连上了（设备下拉里能看到模拟器），但点开始后一直报：

```
MuMu安卓设备未连接，请选择正确的游戏窗口。
Game window is not connected BitBlt_True_0x0
capture_by_bitblt invalid params: hwnd=0, w=0, h=0
```

## 根因

设备切换时 `devices.json` 的抓屏方式（`capture`）残留了上一个设备的值。

具体：`preferred` 已经切到 `MuMuPlayer-15.0-0`，但 `capture` 还是 `"windows"`（从远控窗口 /
PC 设备切过来时只改了设备、没改抓屏方式）。`do_start()` 直接读 `config['capture']`，
见到 `windows` 就走 windows 抓屏分支：

- 该分支把 `preferred['full_path']` 当窗口 exe 去找 hwnd，而那是 **`MuMuNxMain.exe` 启动器**，
  真正的游戏窗口属于 `MuMuNxDevice.exe` → 找不到窗口 → `hwnd=0` → 报"未连接"；
- 而此时 adb（`127.0.0.1:16384`）其实早已连上，MuMu IPC / adb 抓屏都能正常出图——
  纯粹是抓屏方式选错，不是模拟器没起来。

`refresh_emulators()` 里本来就有 `resolve_emulator_window_exe()` 把启动器 exe 解析成窗口 exe，
但 `do_start()` 的 windows 分支漏用了；此前加的 `get_preferred_capture()` 纠偏方法
（capture 与设备类型不匹配时回退到合法值）也没被 `do_start()` 调用。

## 修复

`ok/device/DeviceManager.py`：

1. `do_start()` 改用 `get_preferred_capture()` 的纠偏结果判断抓屏方式：MuMu / adb 设备下
   残留的 `windows` / `browser` 会自动回退到 app config 声明的方式（MuMu 默认 `ipc`），
   不再误入 windows 抓屏分支；
2. `get_preferred_capture()` 纠偏时优先取 `adb.capture_method`（如 `ipc`），
   没有声明再退到第一个可用方法；
3. windows 抓屏分支也用 `resolve_emulator_window_exe()` 解析窗口 exe（双保险：
   即便用户确实想用窗口方式抓模拟器，也不会再拿启动器 exe 去找 hwnd）。

**现有配置不用手动改**：升级后即使 `devices.json` 里还留着 `capture: "windows"`，
启动时也会自动纠偏成 `ipc`。

    无声明退到 adb、windows 设备不受影响；
  - `EmulatorWindowExeTest` 3 项：启动器 exe 解析、`do_start` windows 分支拿到窗口 exe。
- 全量 **305 项通过**（ok-ww 自带 Python）。
