# v1.8.24 — 手机投屏连不上：不是网络问题，是手机端把「这台设备的自动重连」关掉了

v1.8.23 修好了「内核起来就自己退」，内核现在会老老实实等手机上线。
但真机再试还是连不上，而且有一条很关键的对照：

> **同一个手机、同一个局域网，NectarLink 桌面端能连上，ok-ww 的内置内核连不上。**

这句话基本排除了网络、防火墙、端口这一类原因——它们不会只挑一个身份下手。

## 证据链

1. 用 **ok-ww 自己的身份**（`u3kn9obp`）连：QUIC 握手**成功**
   （`network_path=Ip(10.42.31.18->10.42.31.183:36389)`），
   紧接着对端发来 `ApplicationClosed{ error_code: 0, reason: b"reconnect off" }`。
2. 只把 `identity.key` 换成桌面端那份（**数据目录一行不动**）：
   **1 秒内** `connected peer=uo6149gg path=Lan` → `online` → `config` → `ready`，画面正常。
3. 差别只有设备身份。网络是通的，是**手机对这两个身份的态度不同**。

## 根因

nectarlink-core 里，`reconnect off` 这个关闭理由只在一个条件下产生：

```rust
// node.rs:1441
if !self.reconnects(&peer) {
    tracing::debug!(peer = %peer.short(), "refusing session: reconnecting is off for this device");
    conn.close(VarInt::from_u32(CLOSE_NORMAL), b"reconnect off");
    return None;
}
```

`reconnects()` 读**本机** `peer_toggles` 表里这个设备的 `reconnect` 行，缺省为 `true`。
而 ok-ww 那个数据目录里的 `peer_toggles` 表是**空的**（查过 sqlite，0 行）——
**不是我们拒的，是手机拒的**。

也就是说：**手机端数据库里，对 ok-ww 这个 DeviceId 存的 `reconnect` 是 0。**

那能不能从电脑这边把它改回来？**不能。** 查过协议层：`nectarlink-protocol` 里的
`phone.toggles` / `phone.toggle.set` 管的是手机快捷开关（免打扰、铃声、手电筒、
音量、亮度、Wi-Fi、蓝牙……），**没有任何一条消息能改对端的 `reconnect` 开关**。
它只存在手机本地，只有手机 UI 能打开。

### 那到底是什么把它关掉的

手机端只有一个写入点（`Core.kt:3189` `setReconnect`），也只有一个 UI 入口。
问题出在那个按钮：

```kotlin
// HomeScreen.kt
if (device.reconnect && device.wakeState != WakeState.Waking) {
    OutlinedButton(onClick = { onSetReconnect(device.id, false) }) {
        Text(stringResource(if (device.online) R.string.action_disconnect
                            else R.string.action_stop_reconnecting))
    }
}
```

**同一个按钮**：设备在线时显示「断开」，离线时显示「停止重连」，
两者调的都是 `setReconnect(false)`；而恢复用的「重连」按钮，
只在 `!device.online && !device.reconnect` 时才出现。

所以「手机根本没关自动重连」和代码是一致的：
**点一次「断开」结束投屏，实际写进去的是"永久关掉这台设备的自动重连"**。
这两个动作在界面上看起来是一件事，其实不是。

### 顺带纠正 v1.8.23 的一条错误论据

上一版排查时写过「本端日志里没有 `refusing session`，所以不是我们拒的」——
**这条依据是无效的**。那行是 `tracing::debug!`，而内核的日志级别是 `info`，
`debug` 压根不会输出，看不到它不代表它没发生。本版的结论不再依赖它，
而是靠上面第 2 条（换身份立刻连通）+ 空 `peer_toggles` 表。

## 改了什么

### 内核侧（`nectarlink-sidecar-src/src/main.rs`）

- **「先等上线、再请求投屏」合并成「一边等一边试」**。
  这不只是简化：**只有真的发起投屏请求，错误里才带着手机拒绝的理由**。
  光盯着「在线不在线」，永远等不到这句话。
- **认出 `reconnect off` 就立刻收手**：发一条
  `{"type":"notice","code":"reconnect_off","message":"…"}`，然后以中文原因退出。
  以前会一直等到 120 秒超时，再报一句「手机没上线」——把人引去查网络，方向全错。
- 等待期间的 `waiting` 状态保留（每 10 秒一次，界面不会看着像卡死）。

### ok-ww 侧（`src/phone_mirror_engine.py`）

- 新增 `_looks_like_reconnect_off()`，认这句关闭理由。
- **识别必须放在「过滤日常 INFO 日志」之前**：内核是用
  `tracing::info!(%reason, "disconnected")` 打这行的（`node.rs:1573`），
  按原来的过滤规则它会被当成噪声扔掉——**最关键的那一句正好被丢掉**。
  （这条专门写了测试盯住。）
- `failure_reason` 认出来之后返回一句能照做的话，而不是内核那句英文原文：
  「手机端把「这台设备的自动重连」关掉了……请在手机上的 NectarLink 里打开设备列表，
  找到名字是 ok-ww 的这个设备，点一下「重连」，再回来重新投屏。」
- `wait_ready()` 认出拒绝后立刻返回，不再白等 30 秒。

## 验证

- Rust **9 项测试通过**（新增：拒绝理由的识别，且别的网络错误不会被误认成拒绝）；
- Python **462 项通过**（新增 4 项：notice 变成可执行的提示、藏在 INFO 日志里的
  拒绝也能认出来、普通网络错误不被误认、大小写/空值边界），
  失败用例的构造方式是拿假内核真的把这两行打印出来；
- 部署后 `restore.py` 自检：42 个文件在 working / repo 两处均与仓库一致。

## 你需要做的（这一步只能在手机上点）

1. 手机打开 **NectarLink** → 设备列表 → 找到名字是 **ok-ww** 的这个设备 →
   点「**重连**」（该按钮只在设备离线且自动重连已关时才出现）。
2. 重跑 `python restore.py` 并重启 ok-ww（这版换了内核二进制）。
3. 重新投屏。

如果设备列表里**找不到这个设备、或者没有「重连」按钮**：
点 ok-ww 的「配对手机(扫码)」重新配一次——新配对默认是开启自动重连的。

> **以后别在手机上点那个「断开」**：结束投屏请在 ok-ww 这边停。
> 手机上的「断开」同时会把「这台设备的自动重连」永久关掉，而它看起来只是断开一次。

## 说明

按约定本版**不做实机验证**。已验证到的是「拒绝理由能被内核和 ok-ww 认出来、
并变成一句能照做的提示」，这一层用假内核端到端跑通了；
「在手机上点『重连』之后能不能立刻连上」由使用者确认。
