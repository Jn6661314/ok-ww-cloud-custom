# v1.8.25 — 手机投屏「能连上但启动不了」：连是按毫秒算的，框架问得太早

v1.8.24 解决的是「连不上」（手机端把自动重连关了）。这一版是紧接着的下一个问题：

> **内核连上了、画面端口也拿到了，但点开始就是起不来。**

而且日志里有一处很刺眼的自相矛盾：同一秒里既有

```
手机投屏: 已连接投屏内核, 画面端口 64353
```

又有

```
start_device: {..., 'pc_phone_mirror', 'connected': False, ...}
```

「已连接」和 `connected: False` 同时出现，说明**不是没连上，是问得太早**。

## 根因：一个几十毫秒的时序窗口，恰好卡在框架的判断上

### 1. 抓屏通道是异步连的，`start()` 却立刻返回

```python
def start(self):
    self._running = True
    self._thread = threading.Thread(target=self._receive_loop, ...)
    self._thread.start()
    return True          # ← 线程刚拉起来, socket 还没建

def connected(self):
    return self._running and self._socket is not None   # ← 此刻必然是 False
```

`do_start` 里的调用顺序是 `start()` → 紧接着算 `connected()`，中间没有任何等待。
本机回环连上只要 **31 毫秒**，可框架问的那一行正好落在这 31 毫秒里面。

### 2. 这个瞬时值被写回了设备字典

`ok/device/DeviceManager.py` 的 `do_start` 结尾：

```python
preferred['connected'] = self.capture_method is not None and self.capture_method.connected()
```

`update_pc_device()` 里内置引擎的伪设备本来是 `connected: True`，被这一行按「某一瞬间
的 socket 状态」改成了 `False`，并留在 `device_dict` 里给启动流程用。

### 3. 框架对「未连接的 windows 设备」只有两条路，都不是我们要的

```python
# ok/core/start_controller.py:314
def start_device(self, ...):
    device = og.device_manager.get_preferred_device()
    if device and not device['connected']:
        if device['device'] == "windows" and not is_admin():
            communicate.starting_emulator.emit(True, "PC version requires admin privileges...")
            communicate.restart_admin.emit()
            return False
        path = og.device_manager.get_exe_path(device)
        if path:
            ...启动游戏 exe...
        else:
            communicate.starting_emulator.emit(True, "Game path does not exist, Please open game manually!")
            return False
```

内置引擎是个**伪设备**：没有窗口、没有 exe。所以它要么被要求「以管理员身份重启」，
要么走到「游戏路径不存在，请手动打开游戏」——两条路都是死路，任务根本起不来。

**这就是「能连接但无法启动」的全部原因。** 跟网络、跟手机、跟内核都没关系。

## 改了什么

### `ok/device/capture_methods/phone_mirror_socket.py`

- **`start()` 等到真的连上才返回**（最多 3 秒，实测 31ms）。这是根因修复：
  `start()` 返回后 `connected()` 一定是 `True`。
- **连不上就老实返回 `False`**，不谎报 —— 界面会立刻报「连不上画面端口」，
  而不是假装连上然后一直等到超时。
- `connected()` 增加 **8 秒重连宽限**：内核换模式、手机短暂掉线时 socket 会断一下，
  后台线程一秒内重连；这期间的 `connected()` 仍然算已连接，避免框架又把设备判成未连接。

### `ok/device/DeviceManager.py`

- `_use_phone_mirror_engine_capture()`：**同端口已连接就复用**，不再每次启动流程都把
  socket 重建一遍（每次重建都会造出一个新的 31ms 空窗）。连不上时打一条明确的错误。
- `do_start` 里内置引擎的 `connected` **恒为 `True`**：

  > 伪设备没有「外部设备」可以断线，能不能用由 capture 层回答
  > （`check_device_error` 会检查 `capture_method.connected()` 并实际取一帧）。
  > 让设备字典跟着 socket 的瞬时状态跳动，只会把启动流程带到「要求管理员重启」
  > 和「游戏路径不存在」这两条死路上去。

  内核真的没起来时，`_use_phone_mirror_engine_capture()` 仍会等并打出真实原因
  （例如 v1.8.24 那条「手机端关掉了自动重连」），日志里看得到，不会再被
  「游戏路径不存在」顶掉。

## 验证

- Python 全量 **465 项通过**（新增 3 项）：
  1. `start()` 返回时 `connected()` 已经是 `True`（盯住这次的 bug）；
  2. 端口没人监听时 `start()` 返回 `False`、`connected()` 为 `False`（不谎报）；
  3. socket 刚断开的一瞬间 `connected()` 仍为 `True`（宽限生效）。
- 用**正在运行的真实内核**做了一次实测：

  ```
  start() -> True, 用时 31ms
  start 后立刻 connected(): True
  0.5s 收到帧 (1080, 491, 3)
  ```

  即「启动后立刻算已连接」和「画面真的进来」都成立。
- `restore.py` 自检：42 个文件在 working / repo 两处均与仓库一致。
